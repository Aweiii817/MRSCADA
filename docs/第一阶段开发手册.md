## 开篇：预备知识——你需要首先理解的东西

在开始写代码之前，有几个概念必须先搞明白。否则你照着抄都会抄错。

### 1. 什么是"编译"？什么是"构建系统"？

你写的是 C++ 源代码（.cpp 文件），但电脑 CPU 不认识 C++，它只认识机器码（一串 0 和 1）。你需要一个叫"编译器"的程序把 C++ 翻译成机器码。这个翻译过程就叫"编译"。

一个项目可能有几十个 .cpp 文件。如果每次修改一行代码都要重新编译所有文件，太慢了。所以有了**构建系统**——它只重新编译修改过的文件，然后把这些文件"链接"成一个可执行程序（.exe）。

主流的 C++ 构建系统有：

- **Make** — Linux 上最古老的，语法很别扭
- **CMake** — 不直接编译，它先生成 Makefile 或 Visual Studio 工程文件，然后调用真正的编译器去编译。写一份 CMakeLists.txt，可以在 Windows、Linux、macOS 上都能编译
- **QMake** — Qt 早期的构建工具，但 Qt 6 已经转向 CMake

**我们选择 CMake**，因为它是 Qt 6 官方推荐的，也是工业界的标准。

### 2. 什么是"静态库"和"可执行文件"？

- **可执行文件（.exe）**：双击能直接运行的程序
- **静态库（.lib）**：一堆编译好的 .obj 文件打包在一起，不能独立运行，是给其他程序用的。比如我们的 `common` 和 `core` 模块都编译成 .lib，然后 `app` 模块链接它们生成 .exe

好处：修改 common 后只需要重新编译 common，core 和 app 只需要重新链接，不用全部重新编译，快很多。

### 3. 什么是 .h 文件（头文件）和 .cpp 文件（源文件）？

- **.h 文件**：放声明（告诉编译器"存在这样一个函数或类"），比如 `void login(string name);`
- **.cpp 文件**：放实现（这个函数到底怎么工作的），比如 `void login(string name) { /* 检查密码 */ }`

为什么分开？因为 .h 可以被多个 .cpp 文件引用，但 .cpp 的实现在链接阶段只出现一次。一处修改，处处生效。

### 4. 什么是 vcpkg？什么是 manifest 模式？

**vcpkg** 是微软出的 C++ 包管理器，就像 Python 的 pip、JavaScript 的 npm。你需要 spdlog（日志库）和 nlohmann-json（JSON 解析库），不用去官网下载压缩包，vcpkg 自动下载、编译、配置好。

**manifest 模式**：在项目根目录放一个 `vcpkg.json` 文件，列出声明的依赖。执行 CMake 时 vcpkg 自动读取这个文件并安装缺失的包。你不用手动执行 `vcpkg install`。

### 5. 什么是 Qt 的 Signal 和 Slot？

这是 Qt 最核心的机制。想象这样一个场景：你有一个温度传感器类（采集数据），有一个温度显示界面类（显示数据）。传感器采集到新温度后，需要告诉界面"数据变了，请刷新"。

如果用传统方式：界面类要不断轮询（while 循环隔 100ms 读取一次），浪费 CPU。

用 Qt Signal/Slot：传感器类定义一个信号 `temperatureChanged(float value)`，界面类定义一个槽函数 `onTemperatureChanged(float value)`，用 `connect` 连接起来。传感器采集到新数据直接 `emit` 信号，界面自动收到通知。

```
传感器对象::emit temperatureChanged(150.0)
          │
          ▼
Qt 运行时 :: 找到所有 connect 了这个信号的槽函数
          │
          ▼
界面对象 :: onTemperatureChanged(150.0) 被自动调用
```

不需要写轮询代码，不需要手动管理线程。这是 Qt 最大的优势。

### 6. 什么是线程安全？什么是互斥锁（mutex）？

你的程序里有多个线程同时跑。通信线程在不停地写数据（updateTagValue），UI 线程在不停地读数据（getTagValue）。如果两个线程同时操作同一个变量，结果是不确定的——可能读到一半的数据，数值是错的。

**mutex（互斥锁）** 解决这个问题：任何线程想访问共享数据前，先"上锁"，用完再"解锁"。同一时间只有一个线程能持有锁，其他线程必须等待。

### 7. 为什么用 spdlog 而不是直接用 qDebug？

|       | qDebug                    | spdlog                               |
| ----- | ------------------------- | ------------------------------------ |
| 输出到文件 | 不能                        | 能，自动滚动                               |
| 多线程安全 | 不安全                       | 安全                                   |
| 性能    | 一般                        | 异步写入，不阻塞业务线程                         |
| 格式化   | qDebug() << a << b        | spdlog::info("a={}, b={}", a, b)     |
| 日志级别  | 只有 debug/warning/critical | trace/debug/info/warn/error/critical |

最关键的：**生产环境的上位机一定要有日志文件**。操作员做了什么操作、什么时候报警了、什么时候通信断开了，这些都要记录到文件里，出了问题才能追溯。

### 8. 什么是 RAII？

C++ 的核心思想之一：资源获取即初始化。简单说就是——**对象的构造函数分配资源，析构函数释放资源**。

比如 `std::lock_guard<std::mutex> lock(m_mutex)`：构造时给 mutex 上锁，函数结束时 `lock` 对象自动销毁，析构函数自动解锁。就算函数中间抛出异常，锁也会正确释放。

## 第一章：先建目录，再写 CMake

### 1.0 预备知识：什么是 CMakeLists.txt？

每个要编译的目录都需要一个 `CMakeLists.txt`。它是 CMake 的"菜谱"，告诉 CMake：

- 这个目录下有哪些源文件（.cpp）
- 需要链接哪些外部库（Qt、spdlog）
- 最终生成的是什么（.exe 还是 .lib）

我们的项目目录结构是分层的，所以 CMakeLists.txt 也要分层：

```
D:\QtProject\UCS\CMakeLists.txt          ← 顶层：定义项目、查找 Qt、引入子目录
  ├── src/common/CMakeLists.txt           ← 编译 common 静态库
  ├── src/core/CMakeLists.txt             ← 编译 core 静态库
  ├── src/app/CMakeLists.txt              ← 编译 UCS.exe 可执行文件
  └── tests/CMakeLists.txt                ← 编译测试程序
```

每一层只负责自己目录里的文件，不跨层管理。模块化、分而治之。

打开 PowerShell，执行：

```powershell
New-Item -Path "D:\QtProject\UCS" -ItemType Directory -Force
# 然后进入这个目录，后续所有操作都在这里进行
cd D:\QtProject\UCS
```

**为什么是 D:\QtProject\UCS？** 项目规划建议书中选定的路径，后续所有文件的路径都基于它。

现在 `D:\QtProject\UCS\` 是空的。我们接下来要往里面放文件。

### 1.2 写顶层 CMakeLists.txt

**文件路径：** `D:\QtProject\UCS\CMakeLists.txt`

这是整个构建系统的入口。CMake 读取这个文件后才知道怎么编译整个项目。

```cmake
# ============================================================
# 顶层 CMakeLists.txt
#
# 这个文件是 CMake 的起点。cmake 命令执行时，它首先找到
# 这个文件，按里面的指令逐一执行。
#
# 它做五件事：
#   1. 声明这是一个 C++ 项目，使用 C++17 标准
#   2. 找到 Qt 6 的安装位置和需要的模块
#   3. 找到第三方依赖（spdlog、nlohmann-json）
#   4. 加入三个子目录，每个子目录有自己的 CMakeLists.txt
#   5. 如果启用了测试，加入测试子目录
# ============================================================

# cmake_minimum_required：指定 CMake 的最低版本
# 如果用户电脑上的 CMake 低于 3.22，会报错提示升级
cmake_minimum_required(VERSION 3.22)

# project：定义项目信息
# - UCS：项目名称
# - VERSION 1.0.0：版本号
# - DESCRIPTION：一句话描述
# - LANGUAGES CXX：使用 C++ 语言（不是 C 也不是 Fortran）
project(UCS
    VERSION 1.0.0
    DESCRIPTION "Upper Computer System for Chemical Process Control"
    LANGUAGES CXX
)

# ===== C++ 标准设置 =====
# CMAKE_CXX_STANDARD 17：使用 C++17 标准
# 为什么是 C++17 不是 C++11？
#   C++17 引入了 std::variant、std::optional、std::filesystem、
#   std::string_view 等非常好用的特性，代码更安全、更简洁
# CMAKE_CXX_STANDARD_REQUIRED ON：强制要求编译器支持 C++17，
# 如果不支持就报错，而不是默默用旧标准编译
set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

# ===== Qt 自动处理开关 =====
# 这三个 ON 是 Qt 工程的标配，一定要打开

# AUTOMOC：Qt 的 MOC（Meta-Object Compiler）预处理器
# 如果你的头文件里有 Q_OBJECT 宏（比如 MainWindow.h），
# MOC 会生成额外的 C++ 代码来实现信号槽机制。
# 打开 AUTOMOC 后，CMake 自动帮我们调用 moc 程序，不用手动操作。
set(CMAKE_AUTOMOC ON)

# AUTORCC：Qt 的 RCC（Resource Compiler）资源编译器
# 如果你的项目里引用了 .qrc 资源文件（暗色主题 qss、图标等），
# RCC 会把这些文件编译成二进制嵌入到 .exe 中。
# 打开 AUTORCC 后，CMake 自动管理这个过程。
set(CMAKE_AUTORCC ON)

# AUTOUIC：Qt 的 UIC（User Interface Compiler）界面编译器
# 如果你用 Qt Designer 画了 .ui 界面文件，UIC 把它转成 C++ 代码。
# （本阶段我们不用 .ui，全部手写代码，但先开着以防万一）
set(CMAKE_AUTOUIC ON)

# ===== 查找 Qt6 =====
# find_package 是 CMake 查找外部库的标准命令
# REQUIRED：找不到就报错，不让编译继续
# COMPONENTS：我们需要 Qt6 的哪些模块
#
# Qt6::Core       — Qt 核心：信号槽、线程、容器、JSON、XML、文件操作
# Qt6::Widgets    — 桌面 UI：QMainWindow、QDialog、QPushButton 等所有控件
# Qt6::Sql        — 数据库：QSqlDatabase、SQLite 驱动、数据查询
# Qt6::Concurrent — 并行计算：QFuture、QtConcurrent::run 等
#
# 注意：CMAKE_PREFIX_PATH 要在 CMakePresets.json 中设置
# 指向你电脑上 Qt 6.5.3 的安装路径，比如：
#   D:\Qt\6.5.3\msvc2019_64
# 如果不设置，CMake 不知道去哪里找 Qt
find_package(Qt6 REQUIRED COMPONENTS
    Core
    Widgets
    Sql
    Concurrent
)

# ===== 查找第三方库（通过 vcpkg 安装） =====
# spdlog：C++ 日志库，比 qDebug 强大太多了
# nlohmann_json：Header-only 的 JSON 库，只用包含头文件就能用
# 这两个都是 vcpkg manifest 模式自动安装的
find_package(spdlog REQUIRED)
find_package(nlohmann_json REQUIRED)

# ===== 加入子目录 =====
# 注意加入顺序：common 必须在 core 之前，core 必须在 app 之前
# 因为 app 链接 core，core 链接 common，必须先编译依赖的库
# 这里只写 add_subdirectory，实际的编译规则在每个子目录的
# CMakeLists.txt 中定义
add_subdirectory(src/common)
add_subdirectory(src/core)
add_subdirectory(src/app)

# ===== 单元测试（可选） =====
# option 定义一个开关变量 BUILD_TESTING，默认是 ON
# 用户可以通过 -DBUILD_TESTING=OFF 关闭测试编译
# 这样在 Release 构建时可以跳过测试，加快编译速度
option(BUILD_TESTING "Build unit tests" ON)
if(BUILD_TESTING)
    # enable_testing：启用 ctest 支持
    enable_testing()
    # 加入测试子目录
    add_subdirectory(tests)
endif()
```

写完这个文件，它的使命就完成了。CMake 读到它后会去找各子目录中的 CMakeLists.txt。

### 1.3 写 CMakePresets.json

**文件路径：** `D:\QtProject\UCS\CMakePresets.json`

**为什么要这个文件？**

如果没有它，每次编译你要在命令行敲这么长一串：

```powershell
cmake -S . -B build/debug -G "Visual Studio 17 2022" -A x64 `
    -DCMAKE_BUILD_TYPE=Debug `
    -DBUILD_TESTING=ON `
    -DCMAKE_PREFIX_PATH="D:\Qt\6.5.3\msvc2019_64" `
    -DCMAKE_TOOLCHAIN_FILE="D:\Others\Vcpkg\scripts\buildsystems\vcpkg.cmake"
```

有了 CMakePresets.json，只需要：

```powershell
cmake --preset=debug
```

**这个文件怎么工作的？**

它定义了两个"预设"（preset），每个预设包含一组 CMake 参数：

- `configurePresets`：配置阶段的参数（生成器、架构、缓存变量）
- `buildPresets`：编译阶段的参数（引用哪个配置预设）

```json
{
    "version": 6,
    "configurePresets": [
        {
            "name": "debug",
            "displayName": "Debug (MSVC 2022)",
            "description": "Debug 构建 — 带调试符号，优化关闭",
            "generator": "Visual Studio 17 2022",
            "architecture": {
                "value": "x64",
                "strategy": "set"
            },
            "binaryDir": "${sourceDir}/build/debug",
            "cacheVariables": {
                "CMAKE_BUILD_TYPE": "Debug",
                "BUILD_TESTING": "ON",
                "CMAKE_PREFIX_PATH": "D:\\Qt\\6.5.3\\msvc2019_64"
            }
        },
        {
            "name": "release",
            "displayName": "Release (MSVC 2022)",
            "description": "Release 构建 — 全优化",
            "generator": "Visual Studio 17 2022",
            "architecture": {
                "value": "x64",
                "strategy": "set"
            },
            "binaryDir": "${sourceDir}/build/release",
            "cacheVariables": {
                "CMAKE_BUILD_TYPE": "Release",
                "BUILD_TESTING": "OFF",
                "CMAKE_PREFIX_PATH": "D:\\Qt\\6.5.3\\msvc2019_64"
            }
        }
    ],
    "buildPresets": [
        {
            "name": "debug",
            "configurePreset": "debug"
        },
        {
            "name": "release",
            "configurePreset": "release"
        }
    ]
}
```

**每一项的含义：**

| 字段                                 | 值                            | 含义                           |
| ---------------------------------- | ---------------------------- | ---------------------------- |
| `name`                             | "debug"                      | 预设的名字，`--preset=debug` 就是用这个 |
| `generator`                        | "Visual Studio 17 2022"      | 生成 Visual Studio 2022 工程文件   |
| `architecture.value`               | "x64"                        | 编译 64 位程序                    |
| `binaryDir`                        | `${sourceDir}/build/debug`   | 编译产物放在 build/debug 目录下       |
| `cacheVariables.CMAKE_BUILD_TYPE`  | "Debug"                      | Debug 模式（带调试符号）              |
| `cacheVariables.CMAKE_PREFIX_PATH` | "D:\\Qt\\6.5.3\\msvc2019_64" | 告诉 CMake Qt 在哪里              |

### 1.4 写 vcpkg.json

**文件路径：** `D:\QtProject\UCS\vcpkg.json`

**vcpkg 的 manifest 模式是什么？**

传统方式：你要自己下载 spdlog 的源码，自己编译，把 .lib 和 .h 放到特定目录，然后在 CMake 里用 `find_package` 去找。这个过程很麻烦，不同的库编译方式还不一样。

manifest 模式：在项目根目录放一个 `vcpkg.json`，列出需要的库。执行 cmake 时，CMake 会通过 vcpkg 的 toolchain 文件自动读取这个 json，自动下载、编译、配置这些库。你只需要写 `find_package(spdlog REQUIRED)` 就行。

```json
{
    "name": "ucs",
    "version": "1.0.0",
    "description": "UCS Industrial Upper Computer System",
    "dependencies": [
        "spdlog",
        "nlohmann-json",
        "gtest"
    ]
}
```

**三个依赖分别干什么？**

- `spdlog`：日志库，把日志写到控制台和文件
- `nlohmann-json`：JSON 解析/生成库，读写配置文件
- `gtest`：Google Test，单元测试框架

**注意：** 要让 vcpkg manifest 生效，需要在 CMake 配置时指定 toolchain 文件。这个文件在 CMakePresets.json 中通过环境变量 `VCPKG_ROOT` 自动指定。所以运行 cmake 前，确保设置了环境变量：

```powershell
$env:VCPKG_ROOT = "D:\Others\Vcpkg"
```

### 1.5 写 .gitignore

**文件路径：** `D:\QtProject\UCS\.gitignore`

**什么是 .gitignore？**

如果你用 Git 做版本管理，这个文件告诉 Git："这些文件不要纳入版本控制"。编译产物、IDE 配置文件、临时文件都是不应该提交到 Git 仓库的。

```gitignore
# 编译产物目录（完全不要提交）
build/
cmake-build-*/

# Visual Studio 中间文件（每台电脑生成的都不一样）
.vs/
*.user
*.suo
*.sdf

# 编译过程中产生的文件（.exe 已经要了，这些不需要）
*.obj
*.pdb
*.ilk
*.exp

# 操作系统文件
Thumbs.db
.DS_Store
```

**为什么不提交 build 目录？** build 目录里是编译出来的 .obj、.lib、.exe 文件。不同电脑的编译结果可能不同，而且这些文件很大。队友 clone 你的代码后自己用 cmake 编译一次就行了。

### 1.6 写构建脚本

**文件路径：** `D:\QtProject\UCS\scripts\build_debug.ps1`

**为什么需要这个脚本？** 每次编译都要敲两行命令（cmake --preset=debug 和 cmake --build --preset=debug），还要检查错误码。写个脚本一键搞定。

```powershell
# ============================================================
# Debug 构建脚本
#
# 用法：在 PowerShell 中执行
#   .\scripts\build_debug.ps1
#
# 它做两件事：
#   1. cmake --preset=debug — 配置阶段（生成 Visual Studio 工程）
#   2. cmake --build --preset=debug — 编译阶段（真正的编译）
# ============================================================

# $PSScriptRoot 是当前脚本所在的目录（scripts/）
# Split-Path -Parent 取它的父目录，就是项目根目录 D:\QtProject\UCS\
$ProjectRoot = Split-Path -Parent (Split-Path -Parent $PSScriptRoot)
Set-Location $ProjectRoot

Write-Host "[1/2] 配置 CMake (Debug)..." -ForegroundColor Cyan
# cmake --preset=debug 读取 CMakePresets.json 中的 debug 预设
# 它会生成 build/debug/UCS.sln（Visual Studio 解决方案文件）
```

## 第二章：写 common 模块——最底层的工具箱

### 2.0 预备知识

**什么是静态库？**

我们的项目会编译出几个 .lib 文件和一个 .exe 文件：

```
common.lib ← 第一层（日志、配置——谁都要用）
core.lib   ← 第二层（标签、实时数据库——依赖 common）
UCS.exe    ← 最终产品（主窗口、入口——依赖 core）
```

为什么分成多个 .lib？想象你正在开发，修改了 Logger.cpp 里的一行日志格式代码。如果所有代码都编译成一个 .exe，编译器需要把整个项目 50 个 .cpp 全部重新编译一遍——大概要一分钟。但如果你分成了 common.lib、core.lib、app.exe，编译器只重新编译 common.lib（3 个 .cpp），然后重新链接 core.lib 和 app.exe——大概 5 秒。

**什么叫"链接"？**

你的 main.cpp 里调用了 `Logger::initialize(...)`，但这个函数的实际代码在 Logger.cpp 里。编译 main.cpp 时，编译器只知道"存在 Logger::initialize 这个函数"（因为 main.cpp 通过 `#include "Logger.h"` 看到了声明），但不知道函数的机器码在哪里。链接阶段，链接器把 main.obj 和 Logger.obj 拼在一起——main.obj 里调用 Logger::initialize 的地方，填上 Logger.obj 中对应的机器码地址。这个过程叫链接。

静态库就是提前打包好的一堆 .obj 文件。链接器从 .lib 中提取需要的 .obj 来链接。

### 2.1 先写 common 的 CMakeLists.txt

**文件路径：** `D:\QtProject\UCS\src\common\CMakeLists.txt`

这个文件告诉 CMake：把当前目录下的 Logger.cpp 和 ConfigManager.cpp 编译成一个叫 common 的静态库。

```cmake
# ============================================================
# common 库
# 编译为静态库（.lib），被 core 和 app 引用
# 包含日志系统、配置管理、常用工具函数
# ============================================================

# add_library(common STATIC ...) 创建静态库
# STATIC 表示静态库（.lib），SHARED 表示动态库（.dll）
# 我们全部用静态库，部署时只需要一个 .exe，不需要带一堆 .dll
add_library(common STATIC
    Logger.cpp
    Logger.h
    ConfigManager.cpp
    ConfigManager.h
    Utility.h
)

# target_link_libraries：这个库需要链接哪些其他库
# PUBLIC：链接这个库的人也能看到这些依赖（传递依赖）
# 比如 core 链接了 common，core 也可以使用 spdlog
target_link_libraries(common PUBLIC
    Qt6::Core                     # QString、QDateTime 等 Qt 基础类
    spdlog::spdlog                # 日志功能
    nlohmann_json::nlohmann_json  # JSON 解析功能
)

# target_include_directories：指定头文件搜索路径
# ${CMAKE_CURRENT_SOURCE_DIR} 就是当前 CMakeLists.txt 所在的目录
# PUBLIC 表示谁链接 common，谁就能用这里的头文件
target_include_directories(common PUBLIC ${CMAKE_CURRENT_SOURCE_DIR})
```

**为什么要写这三条指令？**

| 指令                           | 如果没写会怎样                                 |
| ---------------------------- | --------------------------------------- |
| `add_library`                | CMake 不知道要编译哪些文件                        |
| `target_link_libraries`      | 链接时找不到 spdlog 和 Qt6::Core 的函数，报 LNK2019 |
| `target_include_directories` | 别人 `#include "Logger.h"` 时找不到文件         |

### 2.2 写 Logger（日志系统）

#### 2.2.0 预备知识

**什么是"日志级别"？**

一个运行中的系统会产生大量信息。有些很重要（"通信断开了！"），有些不那么重要（"正在启动第 5 次数据采集循环"）。我们给每条信息标一个级别：

| 级别    | 颜色  | 含义       | 例子                              |
| ----- | --- | -------- | ------------------------------- |
| TRACE | 灰色  | 最详细的调试信息 | "进入函数 updateTagValue，参数 TE-101" |
| DEBUG | 蓝色  | 开发调试用    | "标签加载完成，共 24 个"                 |
| INFO  | 绿色  | 正常操作信息   | "系统启动完成"                        |
| WARN  | 黄色  | 可以恢复的异常  | "配置文件不存在，使用默认配置"                |
| ERROR | 红色  | 严重错误     | "通信超时，设备 PLC-01 离线"             |

生产环境通常设为 INFO 级别，只记录 INFO 及以上的信息。TRACE 和 DEBUG 只在开发时开启。

**什么是 spdlog 的 sink？**

sink 是 spdlog 的术语，意思是"输出目标"。一个 logger 可以有多个 sink：

- 控制台 sink：输出到黑窗口（开发时看）
- 文件 sink：输出到日志文件（出问题时查）
- 数据库 sink：输出到数据库（不多用）

每个 sink 可以独立设置格式和级别。

#### 2.2.1 写 Logger.h

**文件路径：** `D:\QtProject\UCS\src\common\Logger.h`

头文件只放声明不放实现。就像菜单只写菜名不写做法。

```cpp
// ============================================================
// Logger.h — 日志系统的声明
//
// 作用：封装 spdlog，对外提供简单的宏接口。
// 为什么封装一层？因为如果以后想换日志库（比如换成
// 公司内部的日志系统），只需要改 Logger.cpp 一个文件，
// 所有调用 LOG_INFO 的地方都不需要动。
// ============================================================

// #pragma once：告诉编译器这个头文件只被包含一次
// 防止同一个头文件被多次 #include 导致重复定义错误
#pragma once

// 引入 spdlog 的头文件
// 尖括号 <> 表示从系统路径或 CMake 指定的路径中查找
#include <spdlog/spdlog.h>
#include <spdlog/sinks/stdout_color_sinks.h>   // 控制台彩色输出
#include <spdlog/sinks/rotating_file_sink.h>   // 文件滚动输出

#include <memory>    // std::shared_ptr —— 共享指针
#include <string>    // std::string —— C++ 字符串

// class Logger：定义一个类，类里包含静态函数和静态变量
// 为什么全是 static（静态的）？因为日志系统全局只需要一个实例，
// 不需要每个地方都创建一个 Logger 对象
class Logger
{
public:
    /// @brief 初始化日志系统
    /// 必须在 main 函数的最开始调用，且只调用一次
    ///
    /// @param log_dir    日志文件存放的目录，默认是 "logs"
    ///                   会在程序运行目录下创建 logs/ 文件夹
    /// @param log_level  日志级别，默认 "info"
    ///                   可选：trace / debug / info / warn / error
    /// @param max_size   单个日志文件的最大字节数
    ///                   默认 10MB（10 * 1024 * 1024 = 10485760）
    /// @param max_files  最多保留几个历史日志文件
    ///                   默认 7 个，超过 7 个自动删除最旧的
    ///
    /// 为什么要设 max_size 和 max_files？
    ///   如果不限制，日志文件可能无限增大，占满硬盘。
    ///   限制后，日志文件到达 10MB 就自动切新文件，
    ///   保留最近 7 个文件，最古老的自动删除。
    static void initialize(
        const std::string& log_dir = "logs",
        const std::string& log_level = "info",
        size_t max_size = 10 * 1024 * 1024,
        int max_files = 7);

    /// @brief 获取 spdlog 的 logger 对象
    /// 供宏内部调用，普通代码不需要直接使用
    static std::shared_ptr<spdlog::logger> instance();

private:
    // 私有的静态成员变量：存储 logger 对象的共享指针
    // static：属于类本身，不属于某个对象
    static std::shared_ptr<spdlog::logger> s_logger;

    /// @brief 将日志级别的字符串转换成 spdlog 内部枚举
    /// 比如把 "info" 转成 spdlog::level::info
    static spdlog::level::level_enum parseLevel(const std::string& level);
};

// ========== 便捷宏定义 ==========
// 为什么用宏？因为宏可以自动携带 __FILE__、__LINE__、__FUNCTION__
// 这些预定义宏，在日志中自动记录"这条日志是哪个文件的哪一行写的"
// 普通函数做不到这一点（除非每次手动传参）

// 宏的基本语法：定义名字和替换内容
// 比如 LOG_INFO("温度: {}", temp) 会被替换成：
//   SPDLOG_LOGGER_CALL(Logger::instance().get(), spdlog::level::info, "温度: {}", temp)

#define LOG_TRACE(...)    SPDLOG_LOGGER_CALL(Logger::instance().get(), spdlog::level::trace, __VA_ARGS__)
#define LOG_DEBUG(...)    SPDLOG_LOGGER_CALL(Logger::instance().get(), spdlog::level::debug, __VA_ARGS__)
#define LOG_INFO(...)     SPDLOG_LOGGER_CALL(Logger::instance().get(), spdlog::level::info, __VA_ARGS__)
#define LOG_WARN(...)     SPDLOG_LOGGER_CALL(Logger::instance().get(), spdlog::level::warn, __VA_ARGS__)
#define LOG_ERROR(...)    SPDLOG_LOGGER_CALL(Logger::instance().get(), spdlog::level::err, __VA_ARGS__)
```

**关于 `__VA_ARGS__` 这个语法：**

它是 C/C++ 预处理器提供的"可变参数"宏功能。`LOG_INFO("温度 {}，压力 {}", temp, press)` 中的 `"温度 {}，压力 {}", temp, press` 就是可变参数，被 `__VA_ARGS__` 捕获并原样传递到 `SPDLOG_LOGGER_CALL` 中。

#### 2.2.2 写 Logger.cpp

**文件路径：** `D:\QtProject\UCS\src\common\Logger.cpp`

```cpp
// ============================================================
// Logger.cpp — 日志系统的实现
//
// 主要工作：在 initialize 中创建两个 sink，组合成 logger，
// 设置格式和级别，然后全局使用。
// ============================================================

// 包含自己的头文件，确保声明和实现一致
#include "Logger.h"

// 文件系统操作：create_directories 检查并创建目录
// 需要 C++17 的 std::filesystem 特性
#include <filesystem>

// 时间相关：std::chrono::seconds(3) 用于设置刷盘间隔
#include <chrono>

// 初始化静态成员变量（所有静态变量必须在 .cpp 中定义）
// 这里把它设为 nullptr，表示"还没初始化"
std::shared_ptr<spdlog::logger> Logger::s_logger = nullptr;

void Logger::initialize(const std::string& log_dir,
                         const std::string& log_level,
                         size_t max_size, int max_files)
{
    // ===== 第一步：确保日志目录存在 =====

    // std::filesystem::create_directories 会检查目录是否存在
    // 如果不存在，就逐级创建所有需要的目录
    // 比如 "logs/production/machine1" 会依次创建 logs/、production/、machine1/
    // 如果已经存在，什么都不做
    std::filesystem::create_directories(log_dir);

    // ===== 第二步：创建两个 sink =====

    // stdout_color_sink_mt：控制台输出，带颜色
    // "mt" = multi-thread（多线程安全）
    // 不同的日志级别显示不同的颜色：
    //   TRACE → 灰色，INFO → 白色，WARN → 黄色，ERROR → 红色
    auto console_sink = std::make_shared<spdlog::sinks::stdout_color_sink_mt>();

    // rotating_file_sink_mt：文件输出，自动滚动
    // 参数 1：文件路径，日志写到 logs/ucs.log
    // 参数 2：max_size，单个文件最大字节数
    // 参数 3：max_files，保留文件个数
    // 比如 max_size=10MB, max_files=7：
    //   日志写到 ucs.log，满 10MB 后改名 ucs.1.log，新建 ucs.log
    //   ucs.1.log 满 10MB 后 -> ucs.2.log ... 直到 ucs.7.log
    //   第 8 次滚动时删除最旧的 ucs.7.log
    auto file_sink = std::make_shared<spdlog::sinks::rotating_file_sink_mt>(
        log_dir + "/ucs.log", max_size, max_files);

    // ===== 第三步：把两个 sink 组合成一个 logger =====

    // 把两个 sink 放进 vector，传给 logger 构造函数
    // logger 会同时向两个 sink 输出
    std::vector<spdlog::sink_ptr> sinks{console_sink, file_sink};

    // 创建 logger，名字叫 "ucs"
    // 这个名字在日志格式中不显示，主要用于多 logger 场景区分
    s_logger = std::make_shared<spdlog::logger>("ucs", sinks.begin(), sinks.end());

    // ===== 第四步：设置日志级别 =====

    // 低于这个级别的日志不会被输出
    // 比如级别设为 info，trace 和 debug 的日志就被过滤掉了
    s_logger->set_level(parseLevel(log_level));

    // ===== 第五步：设置日志格式 =====

    // set_pattern 的格式说明：
    // %Y          — 四位年份（2026）
    // %m          — 两位月份（07）
    // %d          — 两位日期（10）
    // %H:%M:%S.%e — 时:分:秒.毫秒（09:30:15.123）
    // %^...%$     — 中间的内容上色（按级别颜色）
    // %l          — 日志级别名称（小写）
    // %v          — 日志正文
    //
    // 最终输出效果：
    //   [2026-07-10 09:30:15.123] [info] 用户 admin 登录成功
    //   [2026-07-10 09:30:15.456] [error] 通信超时 (PLC-01)
    s_logger->set_pattern("[%Y-%m-%d %H:%M:%S.%e] [%^%l%$] %v");

    // ===== 第六步：设置刷盘策略 =====

    // 为什么要手动刷盘？因为 spdlog 为了性能，会在内存中缓存一段日志
    // 然后批量写入文件。但如果程序在这段缓存期间崩溃了，
    // 日志就丢了。所以我们需要：
    //
    // 1. 遇到 error 级别的日志，立即刷盘
    //    因为 error 是最重要的信息，不能丢
    s_logger->flush_on(spdlog::level::err);

    // 2. 兜底策略：每 3 秒自动刷盘一次
    //    即使这 3 秒内没有 error，info 和 warn 也不至于丢太多
    spdlog::flush_every(std::chrono::seconds(3));

    // 日志系统初始化完成，写一条启动日志
    LOG_INFO("====== UCS Logger initialized ======");
    LOG_INFO("Log directory: {}", log_dir);
    LOG_INFO("Log level: {}", log_level);
}

std::shared_ptr<spdlog::logger> Logger::instance()
{
    // 防御性检查：如果 s_logger 还没初始化（为 nullptr）
    // 就创建一个最简单的控制台 logger 作为保底
    // 这样即使有人没调用 initialize 就写日志，也不会崩溃
    if (!s_logger) {
        // stdout_color_mt 是一个快捷函数，相当于创建了一个
        // 只有控制台 sink 的 logger
        s_logger = spdlog::stdout_color_mt("console");
        s_logger->set_level(spdlog::level::info);
        s_logger->set_pattern("[%H:%M:%S.%e] [%^%l%$] %v");
    }
    return s_logger;
}

spdlog::level::level_enum Logger::parseLevel(const std::string& level)
{
    // 字符串匹配，返回对应的 spdlog 级别枚举
    // level_enum 是 spdlog 定义的枚举类型：
    //   trace = 0, debug = 1, info = 2, warn = 3, err = 4, critical = 5
    if (level == "trace")    return spdlog::level::trace;
    if (level == "debug")    return spdlog::level::debug;
    if (level == "info")     return spdlog::level::info;
    if (level == "warn")     return spdlog::level::warn;
    if (level == "error")    return spdlog::level::err;
    if (level == "critical") return spdlog::level::critical;

    // 如果传了不认识的字符串，默认用 info（安全的选择）
    return spdlog::level::info;
}
```

#### 2.2.3 关于 qDebug 重定向

你可能会问："我之前学 Qt 的时候，都是直接用 qDebug() << "hello" 来打日志的，现在为什么不用了？"

**答案：** qDebug 只能输出到控制台。在生产环境中，操作员不会一直盯着黑窗口看。工程师排查问题需要翻日志文件。而且 qDebug 不支持日志滚动——你的日志文件可能一天就涨到几个 GB。

但是 Qt 框架内部也会用 qDebug 输出一些信息（比如 `QWidget: Must construct a QApplication before a QWidget`）。为了让这些信息也走 spdlog 的统一通道，我们在 main.cpp 中调用这个函数：

```cpp
void installQtMessageHandler()
{
    // qInstallMessageHandler 是 Qt 提供的一个全局函数
    // 它允许我们替换掉 qDebug/qWarning/qCritical/qFatal 的默认行为
    //
    // 参数是一个函数指针（lambda 表达式），这个函数会被调用来
    // 处理所有 Qt 内部产生的日志消息
    qInstallMessageHandler([](QtMsgType type,
                               const QMessageLogContext& ctx,
                               const QString& msg) {
        // 根据消息类型，调用不同的 spdlog 宏
        // msg.toStdString() 把 Qt 的 QString 转成 C++ 的 std::string
        switch (type) {
        case QtDebugMsg:
            LOG_DEBUG("[Qt] {}", msg.toStdString());
            break;
        case QtInfoMsg:
            LOG_INFO("[Qt] {}", msg.toStdString());
            break;
        case QtWarningMsg:
            // 警告信息还附带文件和行号，方便定位问题
            LOG_WARN("[Qt] {} ({}:{})",
                     msg.toStdString(),
                     ctx.file ? ctx.file : "?",
                     ctx.line);
            break;
        case QtCriticalMsg:
            LOG_ERROR("[Qt] {} ({}:{})",
                      msg.toStdString(),
                      ctx.file ? ctx.file : "?",
                      ctx.line);
            break;
        case QtFatalMsg:
            // Fatal 是最严重的错误，记录日志后终止程序
            LOG_ERROR("[Qt FATAL] {} ({}:{})",
                      msg.toStdString(),
                      ctx.file ? ctx.file : "?",
                      ctx.line);
            abort();
        }
    });
}
```

这段代码不放在 Logger.h 里，而是放在 main.cpp 的开头，因为 `qInstallMessageHandler` 是对 Qt 全局状态的修改，适合在入口处统一设置。

### 2.3 写 ConfigManager（配置管理器）

#### 2.3.0 预备知识

**什么是 JSON？**

JSON = JavaScript Object Notation，一种轻量级的数据交换格式。它用人类可读的方式描述结构化数据。

```
{
    "name": "张三",
    "age": 30,
    "address": {
        "city": "北京",
        "street": "长安街"
    }
}
```

基本语法：

- `{}` 表示一个对象（类似于 C++ 的 struct）
- `[]` 表示一个数组（类似于 C++ 的 vector）
- `"key": value` 表示一个键值对
- 值可以是：字符串 `"hello"`、数字 `123`、布尔 `true/false`、对象 `{}`、数组 `[]`、空 `null`

**为什么用 JSON 而不用 XML 或 INI 存配置？**

| 格式   | 可读性 | 支持嵌套 | Qt 支持                             | 配置文件大小 |
| ---- | --- | ---- | --------------------------------- | ------ |
| INI  | 好   | 差    | 好(QSettings)                      | 小      |
| XML  | 差   | 好    | 好                                 | 大      |
| JSON | 好   | 好    | 一般(QJsonDocument) + nlohmann_json | 中      |

JSON 综合最好：可读性强、支持嵌套结构（通信协议配置天然是嵌套的：comm → modbus_rtu → port）、第三方库 nlohmann_json 用起来非常舒服。

**什么是单例模式？**

有些类在整个系统中只需要一个实例：

- Logger — 整个系统只有一个日志系统
- ConfigManager — 整个系统只有一份配置
- TagManager — 整个系统只有一套标签定义
- RealTimeDB — 整个系统只有一个数据中枢

单例模式确保：一个类只有一个对象，并提供全局访问点。

实现方式：

```cpp
class ConfigManager {
public:
    static ConfigManager& instance() {  // 全局访问点
        static ConfigManager inst;       // 唯一的静态实例
        return inst;
    }
private:
    ConfigManager() = default;           // 构造函数私有，外部不能 new
    ConfigManager(const ConfigManager&) = delete;  // 禁止拷贝
};
```

这样全局只有 `ConfigManager::instance()` 这一个访问入口，不会出现两份配置互相冲突的情况。

#### 2.3.1 写 ConfigManager.h

**文件路径：** `D:\QtProject\UCS\src\common\ConfigManager.h`

```cpp
// ============================================================
// ConfigManager.h — 配置管理器
//
// 它管理两种配置：
//   1. config.json — 系统运行参数
//      通信参数、存储策略、报警限值等
//      用 JSON 格式，方便人工编辑
//   2. ui_state.ini — 界面状态
//      窗口位置、分割器位置、最近打开的文件等
//      用 QSettings 管理
//
// 为什么分开？系统参数需要人工编辑和版本控制，
// 界面状态是用户个人偏好，不应该提交到 Git。
// ============================================================
#pragma once

#include <QString>
#include <QSettings>
#include <nlohmann/json.hpp>
#include <memory>
#include <string>

// 类型别名：nlohmann::json 这个名字太长，
// 我们用 using 给它起个别名叫 Json，后面代码简洁很多
using Json = nlohmann::json;

class ConfigManager
{
public:
    /// @brief 获取单例实例
    /// 第一次调用时创建，后续每次返回同一个对象
    static ConfigManager& instance();

    /// @brief 初始化配置管理器
    /// @param config_dir 配置文件的存放目录
    ///                   比如传 "config"，就会在程序目录下
    ///                   创建 config/ 文件夹，里面放 config.json
    void initialize(const QString& config_dir);

    // ========== JSON 配置的读写 ==========

    /// @brief 获取 JSON 配置项的值
    ///
    /// @tparam T 返回值的类型（自动推断）
    ///   int: getJsonValue<int>("comm.modbus.port", 502)
    ///   double: getJsonValue<double>("alarm.check_interval_ms", 200.0)
    ///   std::string: getJsonValue<std::string>("system.language", "zh_CN")
    ///   bool: getJsonValue<bool>("storage.compression_enabled", true)
    ///
    /// @param key 键名，支持点号分隔的多层路径
    ///   "comm.modbus_rtu.port" = json["comm"]["modbus_rtu"]["port"]
    ///
    /// @param default_value 如果键不存在，返回这个默认值
    ///   这样即使配置文件被删了某一行，程序也不会崩溃
    template<typename T>
    T getJsonValue(const std::string& key, const T& default_value) const
    {
        try {
            // 从根节点开始，逐层向下查找
            const Json* node = &m_json_config;
            size_t pos = 0;  // 当前解析到的位置

            while (pos < key.size()) {
                // 查找下一个 '.' 的位置
                size_t dot = key.find('.', pos);

                if (dot == std::string::npos) {
                    // 没找到 '.'，说明这是最后一层键名
                    // .at() 在键不存在时会抛出异常
                    // .get<T>() 把 JSON 值转换为 C++ 类型
                    return node->at(key.substr(pos)).get<T>();
                }

                // 找到 '.'，提取当前层的键名
                auto segment = key.substr(pos, dot - pos);
                // 进入下一层
                node = &node->at(segment);
                pos = dot + 1;  // 跳过 '.'
            }
        } catch (...) {
            // 任何异常（键不存在、类型不匹配、JSON 格式错误等）
            // 都返回默认值，保证程序不会因为配置问题崩溃
        }
        return default_value;
    }

    /// @brief 设置 JSON 配置项的值并立即保存到文件
    /// @tparam T 值的类型
    /// @param key 键名，支持点号路径
    /// @param value 要设置的值
    template<typename T>
    void setJsonValue(const std::string& key, const T& value)
    {
        // 与 get 类似的遍历逻辑，但用于写入
        Json* node = &m_json_config;
        size_t pos = 0;

        while (pos < key.size()) {
            size_t dot = key.find('.', pos);

            if (dot == std::string::npos) {
                // 最后一层，设置值
                (*node)[key.substr(pos)] = value;
                break;
            }

            auto segment = key.substr(pos, dot - pos);
            // 如果中间层不存在，先创建空对象
            if (!node->contains(segment)) {
                (*node)[segment] = Json::object();
            }
            node = &(*node)[segment];
            pos = dot + 1;
        }

        // 写回文件
        saveJsonConfig();
    }

    // ========== 界面状态管理 ==========

    void saveWindowState(const QString& window_name, const QByteArray& state);
    QByteArray loadWindowState(const QString& window_name,
                                const QByteArray& default_state = {});
    QSettings& settings();

private:
    // 构造函数私有——外部不能创建 ConfigManager 对象
    ConfigManager() = default;

    // 删除拷贝构造函数和赋值运算符——不能复制
    ConfigManager(const ConfigManager&) = delete;
    ConfigManager& operator=(const ConfigManager&) = delete;

    void loadJsonConfig();
    void saveJsonConfig();

    // 成员变量
    Json m_json_config;                // 内存中的 JSON 配置树
    QString m_config_dir;              // 配置文件目录
    QString m_json_config_path;        // config.json 的完整路径
    std::unique_ptr<QSettings> m_settings;  // QSettings 指针
};
```

**关于模板函数 `template<typename T>`：**

普通函数需要为每种类型写一个版本：`getIntValue(key)`、`getStringValue(key)`、`getBoolValue(key)`——太麻烦。

模板函数可以自动适配类型：

- `getJsonValue<int>("port", 502)` → T = int → 返回 int
- `getJsonValue<std::string>("host", "127.0.0.1")` → T = std::string → 返回字符串
- `getJsonValue<bool>("enabled", true)` → T = bool → 返回 bool

模板在编译时生成代码，效率与手写版本一样高。

```cpp
// ConfigManager.cpp — 配置管理器的实现
// ============================================================
#include "ConfigManager.h"
#include "Logger.h"

#include <QDir>      // QDir：目录操作
#include <QFile>     // QFile：文件读写
#include <fstream>   // std::ofstream：C++ 文件输出流

ConfigManager& ConfigManager::instance()
{
    // 这是 C++11 以后安全的单例实现方式
    // static 局部变量只初始化一次，即使在多线程环境下
    // 后续调用直接返回同一个实例
    static ConfigManager inst;
    return inst;
}

void ConfigManager::initialize(const QString& config_dir)
{
    m_config_dir = config_dir;

    // ----- 确保配置目录存在 -----
    // QDir::mkpath 会创建目录及其父目录
    // 如果目录已存在，什么都不做
    QDir dir(config_dir);
    if (!dir.exists()) {
        dir.mkpath(".");
        LOG_INFO("Created config directory: {}", config_dir.toStdString());
    }

    // ----- 初始化 QSettings -----
    // QSettings 用于存储窗口位置等 UI 状态
    // 使用 INI 格式而不是 Windows 注册表
    //     原因：INI 文件可以随程序一起迁移
    //     注册表的话，拷贝到另一台电脑上窗口位置就丢了
    m_settings = std::make_unique<QSettings>(
        config_dir + "/ui_state.ini",
        QSettings::IniFormat
    );

    // ----- 加载 JSON 配置 -----
    m_json_config_path = config_dir + "/config.json";
    loadJsonConfig();

    LOG_INFO("ConfigManager initialized");
}

void ConfigManager::loadJsonConfig()
{
    QFile file(m_json_config_path);

    if (!file.exists()) {
        // ----- 配置文件不存在，创建默认配置 -----
        // 这是一个空白的 JSON 对象占位
        // 用户运行程序后第一次编辑配置时，会保存到文件
        LOG_WARN("Config file '{}' not found, creating empty defaults",
                 m_json_config_path.toStdString());

        m_json_config = Json::object();
        m_json_config["system"]["language"] = "zh_CN";
        m_json_config["system"]["theme"] = "dark";
        m_json_config["comm"]["modbus_rtu"]["port"] = "COM1";
        m_json_config["comm"]["modbus_rtu"]["baudrate"] = 19200;
        m_json_config["comm"]["modbus_tcp"]["host"] = "127.0.0.1";
        m_json_config["comm"]["modbus_tcp"]["port"] = 502;
        m_json_config["storage"]["data_retention_days"] = 30;

        saveJsonConfig();
        return;
    }

    if (!file.open(QIODevice::ReadOnly)) {
        LOG_ERROR("Cannot open config file: {}",
                  m_json_config_path.toStdString());
        m_json_config = Json::object();
        return;
    }

    try {
        // QByteArray 是 Qt 的字节数组，toStdString() 转成
        // C++ 标准字符串，供 nlohmann/json 解析
        QByteArray data = file.readAll();
        m_json_config = Json::parse(data.toStdString());
        LOG_INFO("Config loaded: {} ({} bytes)",
                 m_json_config_path.toStdString(), data.size());
    } catch (const std::exception& e) {
        // JSON 解析失败（比如配置文件被手动编辑搞坏了格式）
        // 用空配置替代，程序仍然能运行
        LOG_ERROR("Failed to parse config JSON: {}", e.what());
        m_json_config = Json::object();
    }
    file.close();
}

void ConfigManager::saveJsonConfig()
{
    try {
        // dump(4)：将 JSON 对象序列化为字符串
        // 参数 4 表示缩进 4 个空格，这样配置文件用记事本打开
        // 也能整齐地看到层级关系
        std::string json_str = m_json_config.dump(4);

        std::ofstream file(m_json_config_path.toStdString());
        if (!file.is_open()) {
            LOG_ERROR("Cannot write config to: {}",
                      m_json_config_path.toStdString());
            return;
        }
        file << json_str;
        file.close();

        LOG_DEBUG("Config saved to {}", m_json_config_path.toStdString());
    } catch (const std::exception& e) {
        LOG_ERROR("Failed to save config: {}", e.what());
    }
}

void ConfigManager::saveWindowState(const QString& window_name,
                                     const QByteArray& state)
{
    // QSettings 使用分组（group）来组织数据
    // 把窗口位置存在 [MainWindow] 组下
    m_settings->beginGroup(window_name);
    m_settings->setValue("geometry", state);
    m_settings->endGroup();
}

QByteArray ConfigManager::loadWindowState(
    const QString& window_name,
    const QByteArray& default_state)
{
    m_settings->beginGroup(window_name);
    QByteArray state = m_settings->value("geometry", default_state).toByteArray();
    m_settings->endGroup();
    return state;
}

QSettings& ConfigManager::settings()
{
    return *m_settings;
}
```

```cpp
// Utility.h — 通用小工具函数
//
// 全部内联（inline），不需要 .cpp 文件。
// inline 函数必须在头文件中给出完整实现，

#pragma once

// 以下四个头文件分别提供：
#include <QString>       // Qt 字符串
#include <QDateTime>     // Qt 日期时间
#include <string>        // C++ 标准字符串

// 避免名字冲突。比如其他模块也可能有个函数叫 generateId，

/// @brief 获取格式化的当前时间字符串
/// @param format 格式模板，默认 "yyyy-MM-dd_HH-mm-ss"
/// @return 例：2026-07-10_09-30-15

    // .toString(format) 按模板格式化

/// @brief 生成 8 位十六进制随机 ID
/// @return 例：a3f2b1c0
///
/// 有什么用？给每一条报警记录、每一条操作日志分配唯一 ID
/// 方便后续查询和追溯
inline std::string generateId()
{
    // C++11 引入的随机数设施
    // mt19937：梅森旋转算法，高质量的伪随机数生成器
    // random_device：真随机数种子（基于硬件噪声）
    static std::mt19937 rng(std::random_device{}());

    // 0-15 的均匀分布
    static std::uniform_int_distribution<int> dist(0, 15);

    // 16 进制字符表
    static const char* hex = "0123456789abcdef";

    std::string id(8, '0');  // 先创建 8 个 '0'
    for (auto& c : id) {
        c = hex[dist(rng)];  // 每个位置随机填一个十六进制字符
    }
    return id;
}

{

}

/// @brief QString → std::string 的安全转换

{
    return qstr.toStdString();
}
```

## 第三章：写 core/tag——定义"数据长什么样"

### 3.0 预备知识

**什么是"数据点"（Tag）？**

工业上位机本质上是处理"数据"的。一个数据点是工业信号的最小单元。想象一下你走进化工厂的控制室，大屏幕上显示的每一个数字都是一个"数据点"：

```
TE-101:  150.3 °C    ← 反应釜温度（来自温度传感器）
PT-101:  0.85 MPa    ← 釜内压力（来自压力变送器）
LT-101:  72.5 %      ← 液位（来自液位计）
HV-101:  开           ← 阀门状态（开/关）
```

每个数据点都有：

- **位号（tag_name）**：唯一标识，如 "TE-101"
- **描述**：中文说明
- **单位**：°C、MPa、%
- **数值**：当前值
- **质量戳**：数据是否可信（传感器正常？还是断线了？）
- **时间戳**：数据是什么时候采集的

这些信息打包在一起，就是 `TagDataPoint` 结构体。

**什么是 enum（枚举）？**

枚举是一种"有名字的整数"。

```cpp
// 没有枚举的时候，你可能会这样写：
int data_type = 5;  // 5 代表 FLOAT……但 5 是什么意思？记不住

// 有了枚举：
enum class DataType : uint8_t {
    BOOL = 0,
    FLOAT = 5
};
DataType data_type = DataType::FLOAT;  // 清清楚楚
```

好处：

1. 代码自文档化——`DataType::FLOAT` 一看就懂
2. 类型安全——不能把随意一个 int 赋值给 DataType 变量
3. 编译器可以检查 switch 语句是否遗漏了枚举值

**什么是 uint8_t 和 uint64_t？**

C++ 标准库提供的精确宽度整数类型：

- `uint8_t`：8 位无符号整数，取值范围 0~255。占 1 个字节
- `uint64_t`：64 位无符号整数，取值范围 0~18446744073709551615。占 8 个字节
- `uint16_t`：16 位无符号整数，取值范围 0~65535。占 2 个字节

比直接用 `int` 好在哪里？`int` 在不同平台上长度不同（有些 16 位，有些 32 位，有些 64 位）。用精确宽度类型保证跨平台一致性。

### 3.2 写 TagDataPoint.h

**文件路径：** `D:\QtProject\UCS\src\core\tag\TagDataPoint.h`

这个头文件是**整个 UCS 系统中最重要的文件**。理解了这个文件，你就理解了系统里的数据是怎么组织的。

```cpp
// ============================================================
// TagDataPoint.h — 工业数据点的数据结构
//
// 什么是数据点（Tag）？
//   在工业现场，每个传感器、每个执行器、每个计算中间值
//   都对应一个"数据点"。例如：
//   - TE-101 → 温度传感器的实时读数
//   - HV-101 → 阀门的开关状态
//   - AVG_TEMP → 计算机计算的平均温度
//
// 不管数据来自 Modbus（串口）、OPC UA（以太网）还是
// 仿真引擎（模拟），最终都要打包成 TagDataPoint 结构体，
// 发送给 UI 层显示。UI 层不需要知道数据来源，它只看
// TagDataPoint 里的字段。
// ============================================================
#pragma once

#include <string>
#include <cstdint>
#include <cmath>

// ============================================================
// DataType：数据类型枚举
//
// 对应工业 PLC 中最常用的数据类型。
// 注意 uint8_t 表示用 8 位整数（0-255）存储这个枚举值，
// 只占 1 个字节，不浪费内存。
// ============================================================
enum class DataType : uint8_t
{
    BOOL   = 0,   // 布尔量：只有 ON/OFF 两个状态
                   // 比如阀门开/关、电机运行/停止、报警激活/复位
    INT16  = 1,   // 16 位有符号整数：范围 -32768 ~ 32767
                   // Modbus 保持寄存器的默认数据类型
    UINT16 = 2,   // 16 位无符号整数：范围 0 ~ 65535
                   // 计数器、状态字通常用这个
    INT32  = 3,   // 32 位有符号整数：范围 -21亿 ~ 21亿
    UINT32 = 4,   // 32 位无符号整数：范围 0 ~ 42亿
    FLOAT  = 5,   // 单精度浮点数（7 位有效数字）
                   // 最常用的模拟量类型——4-20mA 信号转成浮点数
    DOUBLE = 6,   // 双精度浮点数（15 位有效数字）
                   // 要求高精度计算时使用
    STRING = 7    // 字符串：设备名称、报警文本等
};

// ============================================================
// Quality：数据质量枚举
//
// 为什么需要"质量"？因为工业现场的传感器并不是永远可靠：
//   - 传感器被撞坏了 → 数据无效（BAD）
//   - 信号超出量程 → 数据可疑（UNCERTAIN）
//   - 一切正常 → 良好（GOOD）
//   - 操作员手动输入了一个值 → 覆盖（GOOD_LOCAL_OVERRIDE）
//
// 数值与 OPC UA 标准对齐。OPC UA 是工业自动化领域的
// 通信标准，这样设计方便以后接入 OPC UA 系统。
// ============================================================
enum class Quality : uint8_t
{
    BAD                 = 0,    // 无效：通信断开、传感器故障
    UNCERTAIN           = 64,   // 可疑：超过量程、校准过期
    GOOD                = 192,  // 正常：数据可用
    GOOD_LOCAL_OVERRIDE = 216   // 强制值：操作员手动设置
};

// ============================================================
// TagDataPoint：数据点结构体
//
// 这是系统中"数据"的终极形态。无论原始数据来自哪里，
// 最终都变成这个结构体，在系统内部流动。
//
//       通信线程                        UI 线程
//   ┌──────────────┐             ┌──────────────┐
//   │ Modbus 读到   │  ──打包──→  │ TagDataPoint │  ──显示──→  │ 屏幕 150.3°C │
//   │ 寄存器 100=150│  TagDataPnt│              │            └──────────────┘
//   └──────────────┘             └──────────────┘
// ============================================================
struct TagDataPoint
{
    // ---- 第一部分：标识（这个数据点叫什么？） ----

    /// 位号，如 "TE-101"
    /// 命名规则：
    ///   第一个字母：T=温度 P=压力 L=液位 F=流量 A=分析
    ///   第二个字母：E=检测元件 T=变送器 V=阀门 H=手动
    ///   数字部分：设备序号
    /// 例：TE-101 = 温度检测元件 #101（1号反应釜的第1个温度点）
    std::string tag_name;

    /// 中文描述，如 "反应釜釜内温度"
    /// 用在界面的标签上，操作员看到的是中文而不是 TE-101
    std::string description;

    /// 工程单位，如 "°C"
    /// 显示在数值后面
    std::string unit;

    // ---- 第二部分：数值（这个数据点当前是多少？） ----

    /// 数据类型（BOOL/INT16/FLOAT 等）
    DataType data_type;

    /// 原始值：直接从设备采集到的值
    /// 对于模拟量输入（AI），这是 ADC 原始读数或 mA 值
    /// 对于数字量（DI/DO），用 0.0 表示 OFF，1.0 表示 ON
    double raw_value;

    /// 工程值：经过量程转换后的实际物理值
    /// 转换公式：工程值 = 原始值 × 系数 + 偏移
    ///
    /// 🎯 举例：4-20mA 对应 0-300°C 的温度传感器
    ///   采集到 12mA → 计算 → 工程值 = 150°C
    ///   公式：(12 - 4) × (300 - 0) / (20 - 4) + 0 = 150
    double scaled_value;

    // ---- 第三部分：质量与时间（这个数据点可信吗？什么时候采集的？） ----

    /// 数据质量（BAD/UNCERTAIN/GOOD）
    /// UI 根据这个字段决定显示样式：
    ///   GOOD → 正常显示数字
    ///   BAD  → 显示 "---" 或灰色
    Quality quality;

    /// 数据采集时间的毫秒级 Unix 时间戳
    /// 从 1970-01-01 00:00:00 UTC 到现在的毫秒数
    /// 例：2026-07-10 09:30:00 → 1781074200000
    /// 为什么用毫秒？因为工业采集频率可高达 100Hz（10ms 一次），
    /// 秒级分辨率不够
    uint64_t timestamp_ms;

    // ---- 第四部分：来源（这个数据点从哪来的？） ----

    /// 来源设备名称，如 "PLC-01"、"RTU-02"、"SimEngine"
    std::string source_device;

    /// 在设备内部的地址，如 Modbus 寄存器的地址
    uint16_t source_address;

    /// @brief 判断数据是否"可用"
    /// 质量大于等于 UNCERTAIN 表示数据至少是"可疑"级别，
    /// 可以显示但需要提醒操作员注意
    /// 质量 BAD 表示完全不可用，不应显示
    bool isValid() const
    {
        return quality >= Quality::UNCERTAIN;
    }
};

// ============================================================
// DataConverter：量程转换工具
//
// 工业传感器通常是标准信号输出，需要换算成工程单位。
// 最常见的两种换算方式：
//   1. 线性转换（直线关系）
//      4-20mA → 0-300°C 是一条直线
//   2. 开方转换（平方根关系）
//      差压式流量计的输出与流量的平方成正比
// ============================================================
class DataConverter
{
public:
    /// @brief 线性量程转换
    ///
    /// 🎯 举例说明：
    ///   传感器：4-20mA 对应 -50°C ~ 150°C
    ///   采集到：12mA
    ///   计算：(-50) + (12-4) × (150-(-50)) / (20-4)
    ///        = -50 + 8 × 200 / 16
    ///        = -50 + 100 = 50°C
    ///
    /// @param raw      原始值（如 12.0 mA）
    /// @param raw_min  原始量程下限（如 4.0 mA）
    /// @param raw_max  原始量程上限（如 20.0 mA）
    /// @param eng_min  工程值下限（如 -50.0 °C）
    /// @param eng_max  工程值上限（如 150.0 °C）
    /// @return 工程值（如 50.0 °C）
    static double linearScale(double raw, double raw_min, double raw_max,
                               double eng_min, double eng_max)
    {
        if (raw_max <= raw_min) return eng_min;  // 防止除零
        return eng_min + (raw - raw_min) * (eng_max - eng_min) / (raw_max - raw_min);
    }

    /// @brief 差压式流量计的开方转换
    ///
    /// 原理：差压 △P 与流量 Q 的关系是 Q ∝ √△P
    /// 所以不能直接线性换算，需要先归一化，再开方，再映射
    ///
    /// @param dp        差压值
    /// @param dp_min    差压下限
    /// @param dp_max    差压上限
    /// @param flow_min  流量下限
    /// @param flow_max  流量上限
    /// @return 流量值
    static double sqrtFlow(double dp, double dp_min, double dp_max,
                            double flow_min, double flow_max)
    {
        if (dp <= dp_min) return flow_min;

        // 步骤 1：归一化到 0~1 范围
        double normalized = (dp - dp_min) / (dp_max - dp_min);

        // 步骤 2：开方
        double flow_normalized = std::sqrt(normalized);

        // 步骤 3：映射到流量量程
        return flow_min + flow_normalized * (flow_max - flow_min);
    }
};
```

**为什么 `isValid()` 函数后面有个 `const`？**

`const` 关键字在这里的意思是：调用这个函数**不会修改结构体**。如果误在函数里写了修改成员变量的代码，编译器会报错。

对调用者来说，看到 `const` 就知道："放心，这个函数只是查查数据，不会乱改。"

### 3.3 写 TagManager（标签管理器）

#### 3.3.0 预备知识

**为什么需要 TagManager？**

上位机系统可能有几百个数据点。UI 在显示一个数据时，需要知道：

- TE-101 是什么？（温度传感器）
- 它用什么单位？（°C）
- 它属于哪个设备？（PLC-01）
- 它在设备里的地址是多少？（Modbus 寄存器 100）

这些信息就是"标签定义"。TagManager 管理所有这些标签定义。

**什么是哈希表（unordered_map）？**

想象你有 500 个标签，要找到名叫 "TE-101" 的那个。如果用 vector（数组），你需要从头遍历，平均要查 250 次才能找到。

哈希表（unordered_map）在插入时计算每个键的哈希值（一个整数），然后把这个整数当作索引。查找时直接计算 "TE-101" 的哈希值，然后跳到对应的位置——**不管有多少个元素，查找时间都是常数**，即 O(1)。

```cpp
// 哈希表的工作原理（简化版）：
// key = "TE-101"
// hash("TE-101") = 12345
// index = 12345 % 1000 = 345
// 直接去位置 345 找 —— 一次内存访问，速度极快
```

#### 3.3.1 写 TagManager.h

**文件路径：** `D:\QtProject\UCS\src\core\tag\TagManager.h`

```cpp
// ============================================================
// TagManager.h — 标签管理器
//
// 功能：管理系统中所有"有哪些标签"这个信息。
//
// 这个类承担的角色就像是"公司员工名册"：
//   名册上记录每个员工（标签）的姓名（位号）、
//   职位（数据类型）、部门（所属设备）等信息。
//
// 界面显示数据时，先通过 TagManager 查到这个标签
// 的元信息（单位、量程），再通过 RealTimeDB 获取当前的数值。
// ============================================================
#pragma once

#include "TagDataPoint.h"     // 使用 TagDataPoint 结构体
#include <unordered_map>      // 哈希表：O(1) 查找
#include <vector>             // 动态数组：顺序存储
#include <string>
#include <memory>             // std::unique_ptr：独占所有权指针

class TagManager
{
public:
    /// @brief 获取全局唯一的 TagManager 实例
    static TagManager& instance();

    /// @brief 从 JSON 字符串加载标签定义
    /// @param json_str 一个 JSON 格式的字符串，包含标签列表
    /// @return 成功加载的标签数量（用于检查）
    ///
    /// 每次调用会清空之前的所有标签定义。
    /// JSON 格式见 TagManager.cpp 中的示例。
    size_t loadFromJson(const std::string& json_str);

    /// @brief 通过位号查找标签
    /// @param tag_name 位号，如 "TE-101"
    /// @return 指向 TagDataPoint 的指针（常量，不允许修改）
    ///         如果找不到，返回 nullptr
    ///
    /// 返回指针而不是引用，因为"找不到"是正常情况，
    /// 指针可以用 nullptr 表示"找不到"
    /// 引用没办法表示"不存在"
    const TagDataPoint* findTag(const std::string& tag_name) const;

    /// @brief 查找属于某个特定设备的所有标签
    /// @param device_name 设备名称，如 "PLC-01"
    /// @return 属于该设备的标签指针列表
    std::vector<const TagDataPoint*> getTagsByDevice(
        const std::string& device_name) const;

    /// @brief 获取所有标签
    const std::vector<std::unique_ptr<TagDataPoint>>& allTags() const;

    /// @brief 获取标签总数
    size_t tagCount() const;

    /// @brief 添加或更新一个标签
    /// @param tag 标签的所有权通过 unique_ptr 转移给 TagManager
    void addOrUpdateTag(std::unique_ptr<TagDataPoint> tag);

private:
    // 构造函数私有——单例模式
    TagManager() = default;

    // 禁止拷贝——单例不能被复制
    TagManager(const TagManager&) = delete;
    TagManager& operator=(const TagManager&) = delete;

    // 存储所有标签的 vector
    // 为什么用 unique_ptr？
    //   unique_ptr 表示"独占所有权"。
    //   vector<unique_ptr<T>> 表示 vector 中的每个元素
    //   都是一个独占指针，TagManager 是这些标签的唯一拥有者。
    //   当 TagManager 被销毁时，所有标签自动释放——不需要手动 delete。
    std::vector<std::unique_ptr<TagDataPoint>> m_tags;

    // 哈希表，用于通过位号快速查找标签
    // key = 位号（string），value = 指向 m_tags 中元素的原始指针
    // 为什么不存 unique_ptr？因为所有权已经在 vector 里了，
    // 这里只是"观察者"（只看不拥有）
    std::unordered_map<std::string, TagDataPoint*> m_tag_map;
};
```

**关于 std::unique_ptr：**

`unique_ptr` 是 C++11 引入的智能指针，表示"独占所有权"。

```cpp
std::unique_ptr<TagDataPoint> ptr = std::make_unique<TagDataPoint>();
// 当 ptr 离开作用域时，自动 delete 它指向的对象
// 不需要手动写 delete ptr;
```

好处：不会忘记 delete，不会重复 delete，异常安全。

#### 3.3.2 写 TagManager.cpp

**文件路径：** `D:\QtProject\UCS\src\core\tag\TagManager.cpp`

```cpp
// ============================================================
// TagManager.cpp — 标签管理器的实现
// ============================================================
#include "TagManager.h"
#include "common/Logger.h"        // 日志记录
#include <nlohmann/json.hpp>      // JSON 解析

// 给 nlohmann::json 起个别名
using Json = nlohmann::json;

TagManager& TagManager::instance()
{
    // 静态局部变量——首次调用时创建，后续返回同一个
    static TagManager inst;
    return inst;
}

size_t TagManager::loadFromJson(const std::string& json_str)
{
    // 每次加载前清空旧数据
    m_tags.clear();
    m_tag_map.clear();

    try {
        // 步骤 1：解析 JSON 字符串
        Json j = Json::parse(json_str);

        // 步骤 2：检查格式是否正确
        // 期望的格式：
        //   {
        //     "tags": [
        //       {"tag_name": "TE-101", "description": "...", ...},
        //       {"tag_name": "PT-101", "description": "...", ...}
        //     ]
        //   }
        if (!j.contains("tags") || !j["tags"].is_array()) {
            LOG_ERROR("TagManager: JSON 格式错误——缺少 'tags' 数组");
            return 0;
        }

        // 步骤 3：遍历 JSON 数组，逐个创建标签对象
        for (const auto& item : j["tags"]) {
            // 创建一个新的标签对象（unique_ptr 自动管理生命周期）
            auto tag = std::make_unique<TagDataPoint>();

            // 从 JSON 对象中提取字段
            // item.value("key", "default")：获取 key 的值，
            // 如果 key 不存在，返回第二参数指定的默认值
            tag->tag_name       = item.value("tag_name", "");
            tag->description    = item.value("description", "");
            tag->unit           = item.value("unit", "");
            tag->data_type      = static_cast<DataType>(item.value("data_type", 5));
            tag->source_device  = item.value("source_device", "");
            tag->source_address = item.value("source_address", 0);

            // 步骤 4：数据校验
            // tag_name 是必填字段，空的不能要
            if (tag->tag_name.empty()) {
                LOG_WARN("TagManager: 忽略了一个没有位号的标签");
                continue;
            }

            // 检查位号是否重复
            if (m_tag_map.find(tag->tag_name) != m_tag_map.end()) {
                LOG_WARN("TagManager: 位号 '{}' 重复，已跳过", tag->tag_name);
                continue;
            }

            // 步骤 5：保存标签
            // 先在哈希表中记录：位号 → 对象指针
            // tag.get() 把 unique_ptr 转成原始指针
            m_tag_map[tag->tag_name] = tag.get();

            // 再把所有权转移到 vector
            m_tags.push_back(std::move(tag));
            // 这里 tag 变成 nullptr，因为所有权已经转移
            // 不能再用 tag 变量了
        }

        LOG_INFO("TagManager: 成功加载 {} 个标签", m_tags.size());

    } catch (const std::exception& e) {
        // JSON 解析异常（比如 JSON 格式错误）
        LOG_ERROR("TagManager: JSON 解析失败——{}", e.what());
    }

    return m_tags.size();
}

const TagDataPoint* TagManager::findTag(const std::string& tag_name) const
{
    // 在哈希表中查找
    auto it = m_tag_map.find(tag_name);

    if (it != m_tag_map.end()) {
        // 找到了，返回标签指针
        // it->second 是 TagDataPoint*，是 vector 中对象的地址
        return it->second;
    }

    // 没找到，返回 nullptr（空指针）
    // 调用者需要检查返回值是否为 nullptr
    return nullptr;
}

std::vector<const TagDataPoint*> TagManager::getTagsByDevice(
    const std::string& device_name) const
{
    std::vector<const TagDataPoint*> result;

    // 遍历所有标签，筛选出属于指定设备的
    for (const auto& tag : m_tags) {
        if (tag->source_device == device_name) {
            result.push_back(tag.get());
        }
    }

    return result;
}

const std::vector<std::unique_ptr<TagDataPoint>>& TagManager::allTags() const
{
    return m_tags;
}

size_t TagManager::tagCount() const
{
    return m_tags.size();
}

void TagManager::addOrUpdateTag(std::unique_ptr<TagDataPoint> tag)
{
    // 防御：空的或没有位号的不能添加
    if (!tag || tag->tag_name.empty()) return;

    // 检查是否已存在（通过哈希表判断）
    auto it = m_tag_map.find(tag->tag_name);

    if (it != m_tag_map.end()) {
        // 已存在：替换旧的
        // 遍历 vector 找到同名的，替换
        for (auto& t : m_tags) {
            if (t->tag_name == tag->tag_name) {
                // 更新哈希表指向新对象
                m_tag_map[tag->tag_name] = tag.get();
                // 替换 vector 中的元素
                t = std::move(tag);
                return;
            }
        }
    }

    // 不存在：新增
    m_tag_map[tag->tag_name] = tag.get();
    m_tags.push_back(std::move(tag));
}
```

**关于 std::move：**

`std::move` 不移动任何数据，它只是一个"类型转换"，把左值（有名字的变量）转换成右值（即将销毁的临时值），告诉编译器："这个变量的内容我不用了，你可以抢走它"。

```cpp
auto tag = std::make_unique<TagDataPoint>();
// ... 填充 tag 的字段 ...

m_tags.push_back(std::move(tag));
// 此时 tag 变为 nullptr，它的"所有权"已经转移到 vector 中
// 不能再用 tag 去访问那个对象了
```

## 第四章：写 core/rtdb——数据的"收发室"

### 4.0 预备知识

**我们已经有了什么？**

到目前为止，系统里有：

- **TagManager**：保存了"系统中存在哪些数据点"的元信息（位号、描述、单位、量程）
- 但是！TagManager **不保存数值**。它只保存"叫什么名字、有什么属性"，不保存"当前值是多少"

**现在需要什么？**

我们需要一个"数据收发室"：

1. 通信层（Modbus、OPC UA）采集到数据后，告诉它"TE-101 的最新值是 150.3"
2. 它把这个值存起来
3. 它通知 UI："TE-101 的值变了，请刷新显示"
4. UI 可以随时查询"TE-101 当前是多少？"

这个"收发室"就是实时数据库（RealTimeDB）。

**什么是观察者模式？**

这是一个设计模式。想象你在等快递：

- 普通做法：你每隔 5 分钟去门口看一次（轮询）——浪费你的时间
- 观察者模式：你给快递员留了电话，快递到了他打电话通知你（通知）——不需要你一直关注

Qt 的 Signal/Slot 就是观察者模式的实现：

```
通信线程（被观察者）                    UI 界面（观察者）
    │                                      │
    ├── emit tagValueChanged("TE-101") ───→│── 槽函数被自动调用
    │                                      │── 刷新温度显示
    │                                      │
    ├── emit tagValueChanged("PT-101") ───→│── 刷新压力显示
    │                                      │
```

不需要写 while(true) 循环去检查数据有没有变。

**什么是 mutex（互斥锁）？**

想象一个场景：通信线程在写数据（TE-101 的值从 150.0 变成 150.3），UI 线程在同一时刻读数据。如果没有保护，UI 可能读到这样的数据：

```
{ tag_name: "TE-101", raw_value: 150.5, scaled_value: 150.0, quality: GOOD }
//                              ↑ 值已经更新了           ↑ 质量还是旧值（可能）
//  这叫"数据竞争"——值的一部分是新数据，一部分是旧数据
```

mutex 解决这个问题：任何线程操作共享数据前，必须先"锁门"。锁上了，其他线程在外面等着。操作完了，打开锁，其他线程才能进来。

```cpp
{
    std::lock_guard<std::mutex> lock(m_mutex);
    // 从这里到 } 结束，只有当前线程能访问共享数据
    // 其他线程如果也想 lock，会被阻塞直到当前线程 unlock
}
// 离开 } 时 lock 自动析构，自动解锁（RAII 的好处）
```

### 4.1 写 RingBuffer.h（环形缓冲区）

**文件路径：** `D:\QtProject\UCS\src\core\rtdb\RingBuffer.h`

**为什么需要 RingBuffer？**

实时趋势曲线需要显示"最近 1 分钟的数据变化"。假设 100ms 采集一次，1 分钟就是 600 个点。如果用 `std::vector`，每次新数据来了 `push_back`，数据量持续增长，内存占用越来越大，而且还不断触发内存重新分配。

环形缓冲区解决了这个问题：**固定大小，新数据自动覆盖最旧数据**。内存占用恒定，没有内存分配，性能稳定。

```
环形缓冲区满时的状态：
         head (写指针，下一次要写的位置)
           ↓
+----+----+----+----+----+
| 6  | 2  | 3  | 4  | 5  |   ← 数字表示写入顺序
+----+----+----+----+----+
  ↑                      ↑
 最旧的（下次被覆盖）      最新的

新数据 7 写入后：
         head (移到下一个位置)
           ↓
+----+----+----+----+----+
| 6  | 7  | 3  | 4  | 5  |
+----+----+----+----+----+
```

```cpp
// ============================================================
// RingBuffer.h — 环形缓冲区
//
// 这是一个模板类（template），意味着可以储存任何类型：
//   RingBuffer<int>             ← 存整数
//   RingBuffer<TagDataPoint>    ← 存数据点
//   RingBuffer<double>          ← 存浮点数
//
// 线程安全：用 std::mutex 保护所有操作
//
// 性能特点：
//   - push：O(1) —— 直接写到 head 位置，不需要移动其他元素
//   - readAll：O(n) —— 需要复制 n 个元素
//   - latest：O(1) —— 直接读 head 前一个位置
// ============================================================
#pragma once

#include <vector>
#include <mutex>

/// @tparam T 要存储的数据类型
/// T 必须支持拷贝构造和赋值操作
template<typename T>
class RingBuffer
{
public:
    /// @brief 构造函数
    /// @param capacity 缓冲区容量，默认 600 个元素
    /// 600 的由来：假设 100ms 采集一次，600 点 = 60 秒 = 1 分钟
    explicit RingBuffer(size_t capacity = 600)
        : m_buffer(capacity)      // 创建指定大小的 vector
        , m_capacity(capacity)    // 记录容量
        , m_head(0)               // 写指针从 0 开始
        , m_size(0)               // 一开始什么都没有
    {
    }

    /// @brief 向缓冲区添加一个元素
    ///
    /// 内部流程：
    ///   1. 加锁（防止多个线程同时写）
    ///   2. 把 value 写入 m_head 位置
    ///   3. m_head 向前移动一位（如果到末尾了，回到 0）
    ///   4. 如果还没满，m_size++
    ///   5. 解锁离开
    void push(const T& value)
    {
        std::lock_guard<std::mutex> lock(m_mutex);

        // 写入
        m_buffer[m_head] = value;

        // head 前进（循环）
        m_head = (m_head + 1) % m_capacity;

        // 更新有效元素计数
        if (m_size < m_capacity) {
            ++m_size;
        }
        // 如果 m_size == m_capacity，说明满了
        // 就不增加了，新数据覆盖旧数据
    }

    /// @brief 读取所有有效数据
    /// @return 按时间从旧到新排序的 vector
    ///
    /// 注意：返回的是拷贝副本，不是引用
    /// 这样调用者可以慢慢处理这个数据，不影响缓冲区的继续写入
    std::vector<T> readAll() const
    {
        std::lock_guard<std::mutex> lock(m_mutex);

        std::vector<T> result;
        result.reserve(m_size);  // 预分配空间，避免多次内存分配

        if (m_size == 0) return result;

        // 确定从哪个位置开始读
        // 如果没满：数据从索引 0 开始连续存放
        // 如果满了：数据从 m_head 位置开始（最旧的）
        size_t index = (m_size < m_capacity) ? 0 : m_head;

        // 按顺序读取每个元素
        for (size_t i = 0; i < m_size; ++i) {
            result.push_back(m_buffer[index]);
            index = (index + 1) % m_capacity;
        }

        return result;
    }

    /// @brief 获取最新添加的一个值
    /// @return 最新值的副本
    ///
    /// 如果缓冲区为空，返回默认构造的 T 对象
    T latest() const
    {
        std::lock_guard<std::mutex> lock(m_mutex);

        if (m_size == 0) return T();

        // 最新值在 m_head 的前一个位置
        // 因为每次 push 是先写值、再移动 head
        size_t idx = (m_head == 0) ? (m_capacity - 1) : (m_head - 1);
        return m_buffer[idx];
    }

    /// @brief 当前有效元素个数
    size_t size() const
    {
        std::lock_guard<std::mutex> lock(m_mutex);
        return m_size;
    }

    /// @brief 缓冲区最大容量
    size_t capacity() const
    {
        return m_capacity;
    }

    /// @brief 清空缓冲区
    void clear()
    {
        std::lock_guard<std::mutex> lock(m_mutex);
        m_head = 0;
        m_size = 0;
    }

private:
    std::vector<T> m_buffer;     // 底层存储——动态数组，但一旦构造完成
                                  // 就不再改变大小
    size_t m_capacity;            // 最大容量
    size_t m_head;                // 写指针：指向下一个要写入的位置
    size_t m_size;                // 当前有效元素数量
    mutable std::mutex m_mutex;   // 互斥锁
};
```

**关于 `mutable std::mutex m_mutex` 中的 `mutable`：**

`mutable` 的意思是"即使是 const 函数也可以修改这个成员"。

在 `readAll()` 和 `latest()` 中，我们需要加锁（修改 mutex 的状态），但这两个函数在逻辑上是"只读"的，所以声明为 `const`。用 `mutable` 修饰 mutex，允许 const 函数修改它。

**关于 `template<typename T>`：**

模板让这个类可以用在任何数据类型上：

```cpp
RingBuffer<int> int_buf;               // 存整数的环形缓冲区
RingBuffer<TagDataPoint> tag_buf;       // 存数据点的环形缓冲区
RingBuffer<double> double_buf;          // 存浮点数的环形缓冲区
```

编译器会根据你使用的类型自动生成对应的代码。一份代码，多种用途——这就是模板的威力。

#### 4.2.0 预备知识

**什么是 Q_OBJECT 宏？**

在 Qt 中，如果一个类要使用信号（signals）和槽（slots）机制，必须在类定义的开头写上 `Q_OBJECT`。

```cpp
class RealTimeDB : public QObject
{
    Q_OBJECT     // ← 这个宏让 Qt 的 MOC（Meta-Object Compiler）处理这个类
public:
    ...
signals:         // ← 信号：发送通知
    void tagValueChanged(const QString& tag_name);

private:
    ...
};
```

如果不写 `Q_OBJECT`，信号和槽相关的代码无法工作，编译时会报错。

**RealTimeDB 怎么工作？**

通信线程（或者仿真引擎）采集到数据后，调用：

```cpp
RealTimeDB::instance().updateTagValue("TE-101", 150.3);
```

RealTimeDB 内部：

1. 构造一个 `TagDataPoint` 对象，填入位号、值、时间戳
2. 从 `TagManager` 查询标签的元信息（描述、单位）
3. 存储到 `m_current_values`（哈希表，键=位号，值=最新数据）
4. 同时推入 `RingBuffer`（保存最近的历史数据）
5. 发出 `tagValueChanged("TE-101")` 信号
6. UI 中连接了这个信号的槽函数被自动调用
7. 槽函数查询 `RealTimeDB::getTagValue("TE-101")` 获取最新值
8. 更新界面上的温度显示

整个过程是**事件驱动**的——没有轮询，没有忙等。

```cpp
// RealTimeDB.h — 实时数据库
//
// 这是数据的"交通枢纽"：
//
//   ┌─────────────┐     setTagValue      ┌─────────────┐
//   │  仿真引擎    │───────────────────→   │             │
//   └─────────────┘                       │             │
//                                         │ RealTimeDB  │  ──信号──→ UI 刷新
//   ┌─────────────┐    updateTagValue     │             │
//   │  通信协议    │───────────────────→   │             │
//   └─────────────┘                       └─────────────┘
//
// RealTimeDB 本身不采集数据，它是一个"中转站"。
// 数据从外部流入，通过信号广播给所有关心它的人。
// ============================================================
#pragma once

#include <QObject>            // QObject：所有 Qt 类的基类
#include <unordered_map>      // 哈希表
#include <memory>             // std::unique_ptr
#include "core/tag/TagDataPoint.h"  // TagDataPoint 结构体

public:

    /// @brief 更新标签的值（通信层最常用的接口）
    ///
    /// 🎯 使用场景：
    ///   通信线程从 Modbus 读取到寄存器 100 的值为 150.0
    ///   调用：RealTimeDB::instance().updateTagValue("TE-101", 150.0);
    ///
    /// @param tag_name  位号，如 "TE-101"

    void setTagValue(const std::string& tag_name,
                     double scaled_value,
                     Quality quality = Quality::GOOD_LOCAL_OVERRIDE);

    /// @brief 查询某个标签的最新值
    /// @param tag_name  位号
    /// @param[out] out_value 输出参数——如果找到了，通过这个传出值
    /// @return true 找到该标签，false 没找到
    ///
    /// 为什么用输出参数而不是返回值？
    ///   因为需要区分"找到了但值是 0"和"没找到"两种情形。
    ///   返回值（bool）表示找没找到，输出参数传出值。
    bool getTagValue(const std::string& tag_name,
                     TagDataPoint& out_value) const;

    /// @brief 获取某个标签的最近 N 个历史值

        const std::string& tag_name, size_t count = 100) const;

    /// @brief 获取所有标签的最新值（用于生成快照或报表）
    std::vector<TagDataPoint> getAllLatestValues() const;

signals:
    /// @brief 标签值变更信号
    /// @param tag_name 发生变化的位号
    ///
    /// UI 组件连接这个信号，数据一变自动刷新：
    ///   connect(&RealTimeDB::instance(), &RealTimeDB::tagValueChanged,
    ///           this, [this](QString name) { refreshDisplay(name); });
    void tagValueChanged(const QString& tag_name);

    /// @brief 标签质量变更信号
    /// 通信断开时 quality → BAD，恢复时 quality → GOOD
    void tagQualityChanged(const QString& tag_name, int quality);

private:
    RealTimeDB();
    ~RealTimeDB() override = default;

    // 禁止拷贝
    RealTimeDB(const RealTimeDB&) = delete;
    RealTimeDB& operator=(const RealTimeDB&) = delete;

    // 当前值缓存：key=位号, value=最新数据点
```

```cpp
// ============================================================
// RealTimeDB.cpp — 实时数据库的实现
// ============================================================
#include "RealTimeDB.h"
#include "common/Logger.h"
#include <QDateTime>

RealTimeDB& RealTimeDB::instance()
{
    static RealTimeDB inst;
    return inst;
}

RealTimeDB::RealTimeDB()
    : QObject(nullptr)  // 父对象为 nullptr——手动管理生命周期
{
    LOG_INFO("RealTimeDB initialized");
}

void RealTimeDB::updateTagValue(const std::string& tag_name,
                                 double raw_value, Quality quality)
{
    // ----- 第一步：构造 TagDataPoint -----
    TagDataPoint point;
    point.tag_name = tag_name;          // 位号
    point.raw_value = raw_value;         // 原始值
    point.scaled_value = raw_value;      // 🎯 第一阶段简化：工程值 = 原始值
                                         // 后续阶段会加入量程转换
    point.quality = quality;             // 数据质量
    point.timestamp_ms = QDateTime::currentMSecsSinceEpoch();  // 当前时间

    // ----- 第二步：补充元信息（从 TagManager 查询）-----
    const auto* tag_def = TagManager::instance().findTag(tag_name);
    if (tag_def) {
        // 如果 TagManager 中有这个标签的定义，把描述和单位复制过来
        point.description = tag_def->description;
        point.unit = tag_def->unit;
        point.data_type = tag_def->data_type;
        point.source_device = tag_def->source_device;
        point.source_address = tag_def->source_address;
    }

    // ----- 第三步：线程安全地更新缓存 -----
    {
        // lock_guard 在构造时自动上锁，析构时自动解锁
        // 这个花括号 { } 限定了锁的作用域
        std::lock_guard<std::mutex> lock(m_mutex);

        // 检查质量是否有变化（从 GOOD → BAD 或从 BAD → GOOD）
        auto value_it = m_current_values.find(tag_name);
        if (value_it != m_current_values.end()) {
            Quality old_quality = value_it->second.quality;
            if (old_quality != quality) {
                // 质量变化了！发出单独的信号
                // UI 可以根据这个信号改变显示颜色（绿色→红色）
                emit tagQualityChanged(
                    QString::fromStdString(tag_name),
                    static_cast<int>(quality));
            }
        }

        // 更新最新值
        m_current_values[tag_name] = point;

        // 更新历史缓冲
        auto hist_it = m_histories.find(tag_name);
        if (hist_it == m_histories.end()) {
            // 第一次为这个标签创建历史缓冲
            auto buffer = std::make_unique<RingBuffer<TagDataPoint>>(600);
            buffer->push(point);
            m_histories[tag_name] = std::move(buffer);
        } else {
            // 已经有缓冲了，直接推入
            hist_it->second->push(point);
        }
    }
    // ----- 离开作用域，锁自动释放 -----

    // ----- 第四步：发出值变更信号（在锁外）-----
    // ⚠️ 重要：为什么要在锁外发出信号？
    // 如果槽函数（UI 刷新）中又调用了 RealTimeDB 的方法
    // （比如 getTagValue），而锁还在持有状态，就会死锁
    // ——自己等自己释放锁。这是永远等不到的。
    emit tagValueChanged(QString::fromStdString(tag_name));
}

void RealTimeDB::setTagValue(const std::string& tag_name,
                              double scaled_value, Quality quality)
{
    // 与 updateTagValue 基本相同，但：
    // 1. raw_value 和 scaled_value 都设为同一个值
    // 2. 质量默认为 GOOD_LOCAL_OVERRIDE（操作员干预）
    TagDataPoint point;
    point.tag_name = tag_name;
    point.raw_value = scaled_value;
    point.scaled_value = scaled_value;
    point.quality = quality;
    point.timestamp_ms = QDateTime::currentMSecsSinceEpoch();

    {
        std::lock_guard<std::mutex> lock(m_mutex);
        m_current_values[tag_name] = point;
        auto hist_it = m_histories.find(tag_name);
        if (hist_it == m_histories.end()) {
            auto buffer = std::make_unique<RingBuffer<TagDataPoint>>(600);
            buffer->push(point);
            m_histories[tag_name] = std::move(buffer);
        } else {
            hist_it->second->push(point);
        }
    }
    emit tagValueChanged(QString::fromStdString(tag_name));
}

bool RealTimeDB::getTagValue(const std::string& tag_name,
                              TagDataPoint& out_value) const
{
    std::lock_guard<std::mutex> lock(m_mutex);
    auto it = m_current_values.find(tag_name);
    if (it != m_current_values.end()) {
        out_value = it->second;  // 复制一份传出去
        return true;             // 找到了
    }
    return false;               // 没找到
}

std::vector<TagDataPoint> RealTimeDB::getTagHistory(
    const std::string& tag_name, size_t count) const
{
    std::lock_guard<std::mutex> lock(m_mutex);
    auto it = m_histories.find(tag_name);
    if (it != m_histories.end()) {
        auto all = it->second->readAll();
        // 如果请求的数量少于缓冲区中的数据，只截取最后 count 个
        if (all.size() > count) {
            all.erase(all.begin(), all.end() - count);
        }
        return all;
    }
    return {};
}

std::vector<TagDataPoint> RealTimeDB::getAllLatestValues() const
{
    std::lock_guard<std::mutex> lock(m_mutex);
    std::vector<TagDataPoint> result;
    result.reserve(m_current_values.size());
    for (const auto& [name, point] : m_current_values) {
        result.push_back(point);
    }
    return result;
}
```

### 5.0 预备知识

**什么是 RBAC？**

RBAC = Role-Based Access Control（基于角色的访问控制）。

工厂里的授权规则：

- 小王（操作员）可以看数据和确认报警，但不能改参数
- 李工（工程师）除了操作员的权限，还可以改参数和配方
- 张经理（管理员）什么都能做

如果用"为每个用户分配权限"的方式：

```
小王 = {查看数据, 确认报警}
李工 = {查看数据, 确认报警, 修改参数, 管理配方}
张经理 = {查看数据, 确认报警, 修改参数, 管理配方, 配置通信, 用户管理, ...}
```

新增一个用户时，又得重新分配一遍——麻烦，容易出错。

RBAC 的做法：

```
角色：操作员 → 权限：{查看数据, 确认报警}
角色：工程师 → 权限：{查看数据, 确认报警, 修改参数, 管理配方}
角色：管理员 → 权限：{所有}

小王：角色=操作员
李工：角色=工程师
张经理：角色=管理员
```

新增用户只需要指定角色，角色预设的权限自动继承。

**什么是位掩码？**

用二进制位表示权限。一个 64 位的整数可以表示 64 种不同的权限：

```
uint64_t permissions = 0;

// 第 0 位：查看监控
// 第 1 位：确认报警
// 第 2 位：修改参数
// ...

设置权限：permissions |= (1 << 2)       // 设置第 2 位（修改参数）
判断权限：permissions & (1 << 2)         // 检查第 2 位是否为 1
组合权限：permissions = (1<<0) | (1<<1)  // 同时有查看和确认报警
```

使用枚举让代码更清晰：

```cpp
enum class Permission : uint64_t {
    VIEW_MONITOR = 1ULL << 0,    // 0000...0001
    CONFIRM_ALARM = 1ULL << 1,   // 0000...0010
    WRITE_PARAM = 1ULL << 2,     // 0000...0100
};
Permission p = Permission::VIEW_MONITOR | Permission::CONFIRM_ALARM;
```

```cpp
#include <cstdint>  // uint8_t, uint64_t

// ============================================================
// UserRole：用户角色
// uint8_t：8 位无符号整数，足够表示最多 256 种角色
// ============================================================
enum class UserRole : uint8_t
{
    NONE     = 0,   // 未登录（仅能查看）
    OPERATOR = 1,   // 操作员：监控和确认报警
    ENGINEER = 2,   // 工程师：操作员权限 + 修改参数和管理配方
    ADMIN    = 3    // 管理员：所有权限
};

// ============================================================
// Permission：权限位掩码定义
//
// 每个权限占用一个独立的二进制位。
// 1ULL << N 表示"1 左移 N 位"，即第 N 位为 1。
//
// 为什么用 uint64_t？
//   64 位 = 64 种不同权限，工业上位机够用了。
//   如果不够，可以改成 uint128_t 或两个 uint64_t 组合。
// ============================================================
enum class Permission : uint64_t
{
    VIEW_MONITOR     = 1ULL << 0,   // 查看实时监控
    CONFIRM_ALARM    = 1ULL << 1,   // 确认报警
    WRITE_PARAM      = 1ULL << 2,   // 修改运行参数
    MANAGE_RECIPE    = 1ULL << 3,   // 管理配方方案
    CONFIG_COMM      = 1ULL << 4,   // 配置通信参数
    CONFIG_SYSTEM    = 1ULL << 5,   // 系统配置
    MANAGE_USER      = 1ULL << 6,   // 用户管理（增删改用户）
    VIEW_HISTORY     = 1ULL << 7,   // 查看历史数据
    EXPORT_DATA      = 1ULL << 8,   // 导出数据
    // ... 可以继续添加，总共可到 63
};

// 重载 | 运算符：让两个权限可以"或"在一起
// 例如：Permission::VIEW_MONITOR | Permission::CONFIRM_ALARM
inline Permission operator|(Permission a, Permission b)
{
    return static_cast<Permission>(
        static_cast<uint64_t>(a) | static_cast<uint64_t>(b));
}

// 重载 & 运算符：判断是否拥有某权限
// 例如：user_perm & Permission::WRITE_PARAM
inline Permission operator&(Permission a, Permission b)
{
    return static_cast<Permission>(
        static_cast<uint64_t>(a) & static_cast<uint64_t>(b));
}

// ============================================================
// UserInfo：用户信息结构体
// ============================================================
struct UserInfo
{
    std::string username;        // 登录名（用于登录验证）
    std::string display_name;    // 显示名称（界面展示用，可以是中文）
    UserRole role;               // 角色
    Permission permissions;      // 权限位掩码（运行时根据角色计算得出）
    bool is_active;              // 是否启用（禁用后不能登录）

    /// @brief 检查用户是否具有某项权限
    bool hasPermission(Permission perm) const
    {
        // 按位与：如果 perm 对应的位在 permissions 中为 1，结果就是 perm 本身
        // 例如：permissions = 0b0011, perm = 0b0010
        //   permissions & perm = 0b0010 == perm → true
        return (permissions & perm) == perm;
    }
};

// ============================================================
// 辅助函数
// ============================================================

/// @brief 根据角色获取默认权限集
inline Permission getDefaultPermissions(UserRole role)
{
    switch (role) {
    case UserRole::OPERATOR:
        return Permission::VIEW_MONITOR
             | Permission::CONFIRM_ALARM
             | Permission::VIEW_HISTORY;
    case UserRole::ENGINEER:
        return Permission::VIEW_MONITOR
             | Permission::CONFIRM_ALARM
             | Permission::VIEW_HISTORY
             | Permission::WRITE_PARAM
             | Permission::MANAGE_RECIPE
             | Permission::EXPORT_DATA;
    case UserRole::ADMIN:
        return Permission::VIEW_MONITOR
             | Permission::CONFIRM_ALARM
             | Permission::VIEW_HISTORY
             | Permission::WRITE_PARAM
             | Permission::MANAGE_RECIPE
             | Permission::CONFIG_COMM
             | Permission::CONFIG_SYSTEM
             | Permission::MANAGE_USER
             | Permission::EXPORT_DATA;
    default:
        // 未登录用户没有任何权限
        return static_cast<Permission>(0);
    }
}

/// @brief 获取角色的中文名称（用于界面显示）
inline std::string roleName(UserRole role)
{
    switch (role) {
    case UserRole::OPERATOR: return "操作员";
    case UserRole::ENGINEER: return "工程师";
    case UserRole::ADMIN:    return "管理员";
    default:                 return "访客";
    }
}
```

```cpp
// UserManager.cpp — 用户管理器实现
// ============================================================
#include "UserManager.h"

#include <functional>  // std::hash

UserManager& UserManager::instance()

    static UserManager inst;
    return inst;
}

UserManager::UserManager()
    : QObject(nullptr)
{
    // 初始化访客用户
    m_current_user.username = "guest";
    m_current_user.display_name = "访客";
    m_current_user.role = UserRole::NONE;
    m_current_user.permissions = getDefaultPermissions(UserRole::NONE);
    m_current_user.is_active = true;
}

void UserManager::initialize()
{
    // ----- 创建三个默认用户 -----
    // 第一阶段：内存存储，后续改为 SQLite 持久化
    // 密码用 std::hash 做简单哈希（后续应改为 SHA-256 + Salt）

    // 用 lambda 表达式定义哈希函数
    // [](const std::string& pw) { return ...; } 是一个匿名函数
    auto hashPassword = [](const std::string& pw) -> std::string {
        return std::to_string(std::hash<std::string>{}(pw));
    };

    // 管理员：admin/admin，全部权限
    m_users["admin"] = {
        "admin",
        hashPassword("admin"),
        UserRole::ADMIN,
        true
    };

    // 工程师：engineer/engineer，工程师权限
    m_users["engineer"] = {
        "engineer",
        hashPassword("engineer"),
        UserRole::ENGINEER,
        true
    };

    // 操作员：operator/operator，操作员权限
    m_users["operator"] = {
        "operator",
        hashPassword("operator"),
        UserRole::OPERATOR,
        true
    };

    LOG_INFO("UserManager initialized with {} users", m_users.size());
}

bool UserManager::login(const std::string& username,
                         const std::string& password)
{
    // Step 1：查找用户是否存在
    auto it = m_users.find(username);
    if (it == m_users.end()) {
        LOG_WARN("用户 '{}' 不存在", username);
        emit loginFailed(QString::fromStdString("用户名或密码错误"));
        return false;
    }

    // Step 2：检查账户是否被禁用
    if (!it->second.is_active) {
        LOG_WARN("用户 '{}' 已被禁用", username);
        emit loginFailed(QString::fromStdString("账户已被禁用"));
        return false;
    }

    // Step 3：验证密码
    std::string input_hash = std::to_string(std::hash<std::string>{}(password));
    if (input_hash != it->second.password_hash) {
        LOG_WARN("用户 '{}' 密码错误", username);
        emit loginFailed(QString::fromStdString("用户名或密码错误"));
        return false;
    }

    // Step 4：登录成功——更新当前用户
    m_logged_in = true;
    m_current_user.username = it->second.username;
    m_current_user.display_name = it->second.username;
    m_current_user.role = it->second.role;
    m_current_user.permissions = getDefaultPermissions(it->second.role);
    m_current_user.is_active = true;

    LOG_INFO("用户 '{}' 以 {} 身份登录成功",
             username, roleName(it->second.role));

    emit loginSucceeded(QString::fromStdString(username));
    return true;
}

void UserManager::logout()
{
    m_logged_in = false;
    m_current_user = {"guest", "访客", UserRole::NONE,
                      getDefaultPermissions(UserRole::NONE), true};
    LOG_INFO("用户已登出");
    emit loggedOut();
}

const UserInfo& UserManager::currentUser() const
{
    return m_current_user;
}

bool UserManager::isLoggedIn() const
{
    return m_logged_in;
}

bool UserManager::hasPermission(Permission perm) const
{
    return m_current_user.hasPermission(perm);
}
```

### 6.0 预备知识

**什么是 QMainWindow？**

`QMainWindow` 是 Qt 提供的主窗口类，自带布局框架：

```
┌──────────────────────────────────┐
│ QMenuBar（菜单栏）                │
├──────────────────────────────────┤
│                                  │
│ QToolBar（工具栏，可选）           │
├──────────────────────────────────┤
│                                  │
│ CentralWidget（核心区域）         │    ← 我们把导航栏 + 内容区放这里
│                                  │
├──────────────────────────────────┤
│ QStatusBar（状态栏）              │
└──────────────────────────────────┘
```

我们不需要工具栏（第一阶段用不到），所以会看到：

- 菜单栏（菜单栏在最顶上）
- 中央区域分左右：左边导航列表，右边堆叠页面
- 状态栏在底部

**什么是信号与槽连接？**

connect 函数把"事件"和"处理函数"连接起来：

```cpp
connect(m_login_btn, &QPushButton::clicked,   // 点击按钮事件
        this, &LoginDialog::onLoginClicked);   // 触发这个函数
```

第一个参数：发送信号的对象（按钮）
第二个参数：信号类型（点击）
第三个参数：接收信号的对象（当前对话框）
第四个参数：要调用的槽函数（处理登录）

点击按钮 → Qt 自动调用 onLoginClicked()。

```cpp
        m_password_edit->setFocus();
        return;

        m_password_edit->clear();
        m_status_label->setText("用户名或密码错误，请重试");
        m_password_edit->setFocus();
    }
```

```cpp
/// @brief 将 Qt 框架内部的日志重定向到 spdlog
void installQtMessageHandler()
{
    qInstallMessageHandler([](QtMsgType type,
                               const QMessageLogContext& ctx,
                               const QString& msg) {
        switch (type) {
        case QtDebugMsg:    LOG_DEBUG("[Qt] {}", msg.toStdString()); break;
        case QtInfoMsg:     LOG_INFO("[Qt] {}", msg.toStdString()); break;
        case QtWarningMsg:  LOG_WARN("[Qt] {} ({}:{})", msg.toStdString(), ctx.file ? ctx.file : "?", ctx.line); break;
        case QtCriticalMsg: LOG_ERROR("[Qt] {} ({}:{})", msg.toStdString(), ctx.file ? ctx.file : "?", ctx.line); break;
        case QtFatalMsg:    LOG_ERROR("[Qt FATAL] {} ({}:{})", msg.toStdString(), ctx.file ? ctx.file : "?", ctx.line); abort();
        }
    });
}
```

### 7.0 预备知识

**什么是 Qt 资源文件（.qrc）？**

.qrc 是一个 XML 文件，它列出了一些"要编译进 .exe"的外部文件。

比如我们有 `dark_theme.qss`（样式表）。如果不用 .qrc，这个文件需要和 .exe 放在同一个目录下，用户拷贝程序时也要带上它。如果不小心弄丢了，程序就没了样式，界面可能变得很难看。

用了 .qrc，qss 文件被编译进 .exe 内部。用户无论把 .exe 拷贝到哪里，样式都在里面。程序代码通过 `:/styles/dark_theme.qss` 访问它——冒号前缀表示"从 .exe 内部读取"。

### 7.1 创建默认配置文件

**文件路径：** `D:\QtProject\UCS\resources\configs\default_config.json`

这个文件的内容是 ConfigManager 第一次启动时参考的"模板"。当 `config/config.json` 不存在时，ConfigManager 会使用这里面的默认值创建一份。

```json
{
    "system": {
        "language": "zh_CN",
        "theme": "dark",
        "data_refresh_interval_ms": 200
    },
    "comm": {
        "modbus_rtu": {
            "port": "COM1",
            "baudrate": 19200,
            "data_bits": 8,
            "parity": "None",
            "stop_bits": 1,
            "response_timeout_ms": 1000,
            "poll_interval_ms": 500
        },
        "modbus_tcp": {
            "host": "127.0.0.1",
            "port": 502,
            "response_timeout_ms": 1000,
            "poll_interval_ms": 500
        },
        "opcua": {
            "endpoint": "opc.tcp://localhost:4840",
            "session_timeout_ms": 60000
        },
        "mqtt": {
            "broker": "localhost:1883",
            "client_id": "ucs_client",
            "qos": 1,
            "publish_interval_ms": 5000
        }
    },
    "storage": {
        "database_path": "data/ucs_history.db",
        "data_retention_days": 30,
        "deadband_percent": 0.5
    },
    "alarm": {
        "check_interval_ms": 200,
        "max_active_alarms": 200,
        "ack_required": true,
        "sound_enabled": true
    },
    "display": {
        "decimal_places": 2,
        "trend_max_points": 600
    }
}
```

**每一项的含义：**

`comm.modbus_rtu` 下的参数：

- `port: "COM1"`：串口号，在设备管理器中查看
- `baudrate: 19200`：波特率，要和 PLC 的设置一致
- `data_bits: 8`：数据位，Modbus 通常用 8
- `parity: "None"`：校验位（None/Even/Odd）
- `stop_bits: 1`：停止位
- `response_timeout_ms: 1000`：等待设备回复的超时时间（1 秒）
- `poll_interval_ms: 500`：两次轮询之间的间隔（500 毫秒）

`comm.modbus_tcp` 下的参数：

- `host: "127.0.0.1"`：Modbus TCP 设备的 IP 地址，127.0.0.1 是本地回环地址
- `port: 502`：Modbus TCP 的标准端口号

## 第八章：写单元测试并编译验证

### 8.0 预备知识

**什么是单元测试？**

单元测试是"用代码测试代码"。写一小段程序，调用被测试的函数，检查返回值是否符合预期。

比如我写了一个 `add(1, 2)` 函数，测试代码就是：

```cpp
int result = add(1, 2);
// 如果 result != 3，测试失败，说明 add 函数写错了
assert(result == 3);
```

**为什么需要单元测试？**

1. **防止改出 bug**：你改了 TagManager.cpp 里的一行代码，可能破坏了一个隐藏的功能。运行测试，如果之前通过的测试现在失败了，你马上就知道有问题
2. **文档即代码**：测试代码展示了"这个函数应该怎么用、预期结果是什么"
3. **信心**：有测试覆盖的代码，重构起来更有底气

**什么是 Google Test？**

GTest 是 Google 开发的 C++ 测试框架。它提供：

- `TEST()` 宏：定义测试用例
- `EXPECT_EQ(a, b)`：检查 a == b，不等则测试失败
- `TEST_F()`：测试夹具，用于多个测试共享相同的初始化代码

```cpp
// ============================================================
// RingBuffer 单元测试
//
// 测试内容：
//   1. 空缓冲区正确返回空
//   2. 推入和读取顺序一致
//   3. latest() 返回最新值
//   4. 溢出时自动覆盖最旧数据
//   5. clear() 正确清空
//   6. 大量写入时容量稳定
// ============================================================
#include <gtest/gtest.h>
#include "core/rtdb/RingBuffer.h"

// 测试 1：新建的缓冲区应该是空的
TEST(RingBufferTest, ShouldBeEmptyInitially)
{
    RingBuffer<int> buf(5);    // 容量为 5
    EXPECT_EQ(buf.size(), 0);               // 大小应为 0
    EXPECT_TRUE(buf.readAll().empty());       // 读取结果应为空
}

// 测试 2：推入数据后，readAll 应保持顺序
TEST(RingBufferTest, ShouldPreserveOrder)
{
    RingBuffer<int> buf(5);
    buf.push(10);
    buf.push(20);
    buf.push(30);

    EXPECT_EQ(buf.size(), 3);               // 现在有 3 个元素
    auto data = buf.readAll();
    ASSERT_EQ(data.size(), 3);               // 读取到 3 个
    EXPECT_EQ(data[0], 10);                  // 最先推入的在索引 0
    EXPECT_EQ(data[1], 20);
    EXPECT_EQ(data[2], 30);                  // 最后推入的在索引 2
}

// 测试 3：latest() 返回最新推入的值
TEST(RingBufferTest, ShouldReturnLatestValue)
{
    RingBuffer<int> buf(5);
    buf.push(100);
    EXPECT_EQ(buf.latest(), 100);   // 最新值 = 100
    buf.push(200);
    EXPECT_EQ(buf.latest(), 200);   // 最新值 = 200
}

// 测试 4：推入超过容量的数据，最旧的应该被覆盖
TEST(RingBufferTest, ShouldOverwriteWhenFull)
{
    RingBuffer<int> buf(3);  // 容量只有 3
    buf.push(1);    // [1]
    buf.push(2);    // [1, 2]
    buf.push(3);    // [1, 2, 3] ← 满了
    buf.push(4);    // [4, 2, 3] ← 1 被覆盖

    EXPECT_EQ(buf.size(), 3);            // 容量仍是 3
    auto data = buf.readAll();
    ASSERT_EQ(data.size(), 3);
    EXPECT_EQ(data[0], 2);               // 现在最旧的是 2
    EXPECT_EQ(data[1], 3);
    EXPECT_EQ(data[2], 4);               // 最新的是 4
}

// 测试 5：清空后重新变为空
TEST(RingBufferTest, ShouldBeEmptyAfterClear)
{
    RingBuffer<int> buf(5);
    buf.push(1);
    buf.push(2);
    buf.clear();
    EXPECT_EQ(buf.size(), 0);
    EXPECT_TRUE(buf.readAll().empty());
}

// 测试 6：大量写入测试——验证容量稳定
TEST(RingBufferTest, ShouldHandleLargeNumberOfWrites)
{
    RingBuffer<int> buf(1000);    // 容量 1000
    for (int i = 0; i < 10000; ++i) {
        buf.push(i);               // 写入 10000 个
    }
    EXPECT_EQ(buf.size(), 1000);   // 容量仍是 1000
    auto data = buf.readAll();
    EXPECT_EQ(data[0], 9000);      // 最旧的是 9000（10000-1000）
    EXPECT_EQ(data[999], 9999);    // 最新的是 9999
}
```

### 你学到了什么？

第一阶段的核心知识点：

1. **CMake 构建系统**：`add_library` vs `add_executable`、`target_link_libraries`、`find_package`、`AUTOMOC`
2. **vcpkg manifest 模式**：通过 `vcpkg.json` 自动管理第三方依赖
3. **spdlog 日志**：sink（输出目标）、日志级别、滚动策略、QSS 样式表
4. **单例模式**：全局唯一的类，`static` 局部变量的线程安全
5. **模板和枚举**：`template<typename T>` 让 RingBuffer 支持任意类型，`enum class` 类型安全的枚举
6. **Qt 信号槽**：`connect` + `emit`，观察者模式的 Qt 实现
7. **线程安全**：`std::mutex` + `std::lock_guard` 保护共享数据
8. **RAII**：`unique_ptr` 自动释放内存，`lock_guard` 自动解锁
9. **RBAC 权限模型**：角色 → 权限，位掩码存储
10. **QMainWindow 布局**：菜单栏 + 导航栏 + 堆叠页面 + 状态栏
11. **Google Test**：`TEST_F`、`EXPECT_EQ`、`ASSERT_NE`
12. **H 树形布局**：`QVBoxLayout`、`QHBoxLayout`、`QFormLayout`、`QStackedWidget`
